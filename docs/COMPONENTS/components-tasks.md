# Tasks workspace components

The `/tasks` workspace: the capture row, the scope tabs and List/Board toggle,
the view toolbar (group/filter/sort/hide-closed), the grouped dense list or the
status board (drag between columns, per-column capture), the row/card inline
status/priority/due pickers, the row actions, and the right slide-over task
panel. Bucketing itself is
server-side (`lib/domain/tasks.ts`, `lib/services/tasks.ts`); grouping, sorting
and filtering are client-side pure projections (`lib/domain/taskViews.ts`) and
the toolbar state is URL-backed (`lib/ui/taskViewParams.ts`). These components
render what the server returns and turn actions into PATCH/DELETE calls. The
page-scoped keyboard triage layer
(`lib/ui/useTaskShortcuts.ts`, mounted by `TasksShell`) and the global `Shift+K`
capture live alongside them; `GlobalCapture` itself is documented in
[`components-shell-and-sidebar.md`](components-shell-and-sidebar.md), because
`AppShell` mounts it on every route.

`app/(app)/tasks/page.tsx` is documented in
[`app-routes.md`](app-routes.md#appapptaskspagetsx) — the repo rule is one
`###` section per file, and every `app/` route lives in `app-routes.md`, so the
page cannot appear here as well.

**Read this when** a row action does nothing, a task shows in the "wrong"
bucket, a touch target is too small, or an E2E spec cannot find a control: the
accessible-name patterns are listed per component below.

### components/tasks/TasksShell.tsx

**Purpose** — The client workspace under the server page: the capture row, scope tabs, view toolbar, grouped dense list (with its loading, error and empty states), the right slide-over task panel and the page-scoped keyboard triage/undo layers. It is the only owner of `TaskViewState` (layout/group/sort/closed/filters, URL-backed), the scope, the row selection, the open panel task, the per-task `TaskActions` closures and the task/collection mutations.

**Public API** — `export function TasksShell(props: { timezone: string; weekStartsOn: 0 | 1; shortcutsEnabled: boolean; timeFormat: TimeFormat; currentUserId: string })`. No other exports. It mounts `TaskPanel` itself (opened by `Enter`, a row title/`Open`, and the `?task=<id>` deep link), binding the panel's `actions` to the open task and overriding `onDelete` to close the panel first; it threads `timeFormat` and `timezone` down to `TaskBoard`, `TaskList` and `TaskPanel` so every due chip renders the household time and its `TimeField` picker marks "now" in the household zone.

**State & side effects** — `state: TaskViewState` is initialised once from `useSearchParams()` with `parseTaskViewState` and written through `updateState(next)`: `setState(next)` plus `router.replace("/tasks?" + mergeTaskViewParams(searchParams, next))` (never `push`, so Back leaves `/tasks` instead of undoing each toolbar click). The reverse direction is a render-time sync keyed by the query string (`searchKey`/`syncedSearchKey`, the React "adjust state when a prop changes" pattern): a Back/Forward or a pasted link re-parses `layout`/`group`/`sort`/`closed`/`status`/`priority`/`list`, and the equal parse schedules no extra render. The scope is URL state too: `view: TaskScope` initialises from `?view=` through `parseTaskScope` (unknown, absent and the retired `inbox` all fall back to `"all"`), the same sync block re-reads it on Back/Forward, and `changeScope`/`updateState`/`clearTaskParam` all write it back through `mergeTaskScopeParams` with `router.replace` — a real scope sets `view` and All deletes it — so `/tasks?view=today` is shareable, `/tasks` is All, and switching back to All drops a stale `view`. A `?view=` value that is not one of the three time scopes, or an explicit `view=all`, is also stripped from the URL on every incoming query string (mount and Back/Forward), so an old link cannot keep claiming a scope the page is not showing; All is canonically absent. Local `collapsedGroups: Record<string, boolean>` (absent = open; the board has no collapse), `selectedTaskId: string | null`, `editorTask: TaskView | null` (`null` means closed), `helpOpen`, and the derived `panelTask` (the live row for `editorTask`'s id while it is in the payload, otherwise `editorTask`, which `patch` refreshes from every successful PATCH echo). Queries: `useTasks(view, state.collectionId ?? undefined, state.closed)` over the four-part key `["tasks", view, collectionId ?? null, closed ? "closed" : "open"]` (`/api/tasks?view=&collectionId=&includeClosed=true`) and `useCollections()` (`["collections"]`, for the Move-to-list submenu and the filter's list). `counts` comes from the same payload and stays `undefined` until it lands (loading/error render no badges); `today` is `useMemo(() => localToday(timezone), [timezone])`. Rows are a pure projection: `sortTasks(filterTasks(tasks, { status, priority, collectionId }), sort)`; in list layout it is split by `groupTasks(..., group)`, while in board layout it is always split by **status** (the board is grouped by status by definition, and the toolbar's Group control is disabled there), so the flattened `visibleRows` is exactly the painted order in both layouts — column order on the board, group order in the list. `visibleRows` excludes a collapsed group's rows (collapse is owned here, not in `TaskList`, precisely so the selection cannot land on an unpainted row). `visibleRows` is what the selection/`j`/`k`/coherence effect all use. Mutations: `useUpdateTask` for complete/uncomplete and the status picker (`status`, including `in_progress`), the priority picker (`priority`), the due chip and the `1`/`2`/`3` keys (`dueOn`/`dueTime`; `3` clears the due date and time — an already-undated row toasts `Already in Someday`), the panel's inline title (`patchTitle`) and checklist (`patchChecklist`), with the panel's notes on its own `useUpdateTask`, Move/the `4` key (`collectionId` + `sortOrder` on undo) and Drop; `useDeleteTask` for Delete and `useCreateTask` for the delete-undo re-create. Failure toasts: status paths `Could not update the task.`, priority `Could not update the priority.`, the due chip `Could not update the due date.`, Move `Could not move the task.`, Delete `Could not delete the task.`; `4` with no other writable list toasts `No other writable list to move to.`, while `3` toasts `Due date cleared` after clearing a dated row (with the due-restoring undo) and `Already in Someday` for an undated row (the Inbox is a list, not a bucket). `useUndoHotkey()` is mounted here, so `z`/`Ctrl+Z` work on `/tasks` exactly as on the calendar. `TaskToolbar`'s Add task focuses the capture input by the `#task-capture` id; choosing Board sets `layout=board` in the URL, and the shell renders `TaskBoard` in place of the list (the toolbar's Group control is disabled there because a board is always grouped by status).

**Undo contract (targeted)** — Every successful complete/reopen/start/drop/delete/due/priority/move calls `pushUndo` with a compensating action and shows `undoToast(message, handle)` (`lib/ui/undoToast.ts`), so the toast's Undo reverts *that* action and not whatever landed last. The stack labels are `Complete task` / `Start task` / `Reopen task` / `Drop task` / `Delete task` / `Set due date` / `Change priority` / `Move task`; `z`/`Ctrl+Z` consume the shared stack LIFO. A PATCH whose server echo equals the previous row (status, priority, due date and time, or the same collection) pushes **no** action — the toast would be a lie.

| Action | Undo (compensating request) |
|---|---|
| Complete / start / reopen / drop | one PATCH back to the previous `status` |
| Status pill, priority flag | one PATCH back to the previous `status` / `priority` |
| Due chip, `1`/`2`, `3`'s clear-due | one PATCH restoring the previous `dueOn` + `dueTime` |
| Move (menu, `4`) | PATCH `collectionId` back to the source list, then PATCH `sortOrder` (a move always appends, so the position needs the second request) |
| Delete | `POST /api/tasks` with the captured `title`/`notes`/dates/`collectionId`/**`priority`** (plus `status: "in_progress"` when the deleted row was in progress), then one PATCH — only when it has something to say — restoring `checklist`, `sortOrder` and a `done`/`dropped` `status` (the service stamps the audit timestamps on that transition), so an urgent or finished task comes back urgent or finished; the re-created task gets a **new id** (there is no trash table). Both payloads are built by `lib/ui/taskUndo.ts` and pinned by `tests/unit/task-undo.test.ts` |
| Panel title / notes / checklist | **no** undo and no success toast: the inline title is reverted by retyping, and notes/checklist keep the v0.2.0 editor's silent save (failures still toast) |

**`?task=` deep link** — A calendar task chip pushes `/tasks?task=<id>`. `TasksShell` reads `useSearchParams()`; the param is one-shot, and the handled marker is set by `deepLinkHandledRef` **only once the lookup settles** (`lib/ui/taskDeepLink.ts`). That ordering is required, not stylistic: `next.config.ts` sets `reactStrictMode: true`, so development runs the effect's setup → cleanup → setup, the first `GET /api/tasks/{id}` closure is cancelled before its response, and an early marker would make the second setup return while that cancelled closure owns the only answer — no panel would ever open. The in-flight promise is cached in a ref keyed by the param, so the second setup awaits the same request and the marker is set at the settle site. The effect prefers the row from the current (unfiltered) view through `tasksRef`, so arriving rows do not re-run it; otherwise it uses the `GET` — a chip task can be outside the current scope (e.g. dated beyond this week while Someday is open), so the `GET` is the normal path, not a fallback. A 404/403 toasts and drops only `?task=` from the live URL, keeping the toolbar params. `closeEditor()` (the close button, Escape, Delete) also removes the param through `clearTaskParam()` (merge the current state, delete `task`, `router.replace`), so a reload or Back does not reopen a dismissed panel; the scope is kept in the URL as `?view=` for a real scope (`/tasks` alone means All).

**Selection and the shortcut contract** — `useTaskShortcuts(shortcutsEnabled, …)` is mounted here, so every key is page-scoped and inert when the preference is off. `j`/`k` clamp through `visibleRows` (the grouped render order; from no selection `j` lands on the first row and `k` on the last), set `selectedTaskId` and call the row's `focus()`; clicking or tabbing into a row selects it through `TaskRow.onFocus`. `1` sets `dueOn = localToday(timezone)`, `2` sets `dueOn = endOfWeek(today, weekStartsOn)` (on the household week's last day this equals today, so the task shows in Today per D6), `3` clears the due date and its time (an already-undated row toasts `Already in Someday` instead of making a no-op PATCH); `4` cycles to the next writable list, `x` PATCHes `status: "done"`, `Enter` opens the panel for the selection, `?` opens `TaskShortcutHelpDialog` (also the "Keyboard shortcuts" button beside the scope tabs) and `Escape` clears the selection. Switching the scope clears the selection but keeps layout/group/sort/filters (they live in the URL). All keys share `isTextEntryTarget`/`hasOpenOverlay`, so typing in the capture input or any open dialog/menu/popover never moves the selection; `Enter` on a focused button (checkbox, title, pickers, menu, tabs) is left to that control instead of opening the panel.

**Selection coherence** — Complete, start, drop, delete, due, priority and Move can all remove the selected row from the visible rows once the settle refetch (or a filter/group change) paints. A `useEffect` over `visibleRows` compares the selection using `previousTasksRef` (the last rendered rows): when the selected id no longer exists, the stale id is cleared and the selection moves to the row that took its place (`min(oldIndex, length − 1)`, falling back to the first row) and that row is focused, because focus follows selection. When nothing is visible, focus goes to the current scope tab (`TaskViewTabs.activeRef`) — not the capture input, which would swallow `j` as typed text. While the panel is open the selection still moves (the panel is non-modal and the list keeps painting underneath) and `closeEditor` focuses the live selection on the next paint, falling back to the scope tab. The effect never runs while the query is pending or on a scope switch (the selection is null then), so a following `j`/`x`/`1` acts on a real row instead of silently no-opping on a vanished id. A collapsed group's rows are **not** in `visibleRows` (collapse state lives in the shell), so `j`/`k` never lands on a row the user cannot see; collapsing a group that holds the selection **clears** the selection inside `toggleGroup` first, so the coherence effect has nothing to move and focus stays on the header the user just activated instead of being pulled into another group's row. The one documented edge is the query-key change itself: `previousTasksRef` is overwritten with `[]` while a filter/closed query is pending, so the first repaint after such a change falls back to the first row rather than the nearest one.

**Panel wiring** — `openTask(task)` selects the row and sets `editorTask`; the rendered `panelTask` is the live row for that id while the payload still holds it and `editorTask` once a mutation removes it, and `patch`'s `onSuccess` refreshes `editorTask` from the saved echo, so completing/dropping from the panel cannot rewind it to the open-time status when the settle refetch drops the row from an open-only view. `closeEditor` clears it (and the `?task=` param when present) and restores focus to `li[data-selected="true"]` (or the scope tab when the edit re-bucketed the last row out of the view). The panel's Delete is the same `deleteTaskWithUndo` as the row menu, with `closeEditor` first so the undo toast is not hidden behind the panel; both paths push the same undo. Escape is consumed by the panel (capture phase + `stopPropagation`), so the shell's `Escape` selection-clearing never fires on the same key.

**Task chips are tasks, not events** — On the calendar (`/`), `CalendarShell` draws due-dated **active** tasks (`isActiveStatus`: open or in_progress) through `components/calendar/taskChip.ts` as read-only all-day FullCalendar events on their due date (the time of day is not shown on the grid), with ids `task:<id>` and `extendedProps.kind = "task"`. Chips join the same `events` array as the event occurrences: they inherit the grid's stacking, `dayMaxEventRows`/`eventMaxStack` and the built-in "+N more", so a day full of chips folds exactly like a day full of events. A click is branched in `CalendarShell.handleEventClick` to `router.push("/tasks?task=<id>")` — never the event details popover, event edit form, drag or resize. `data-task-id` and `aria-label="Task: <title>"` are set by `CalendarView.eventDidMount`. Rendering is read-only: a task chip's only interaction is the deep link; re-dating happens through the row's due chip or by dragging the row. Only active (`open`/`in_progress`) rows draw, so the optimistic task cache holding a just-completed/dropped row for a beat cannot paint a chip for finished work — and an in-progress task is not flagged `completed`. **Accepted superset (controller ruling):** because a chip is an all-day event on the one shared `events` array, it also appears in the Week, Day and List views; those grids are read-only for chips too (no drag/resize, click = task panel), and only the month day cells attach task-drop listeners.

States: `isError` renders `role="alert"` with "Could not load the tasks." and a "Try again" retry button; `isPending` renders `role="status"` "Loading tasks…"; zero visible groups render `TaskList`'s empty state — "No tasks match these filters." with a Clear-filters button when a status/priority/list filter is active, otherwise exactly "Nothing here. Enjoy the quiet.". The root `<section aria-label="Tasks" data-testid="tasks-shell">` also carries `data-week-starts-on` and `data-shortcuts-enabled` as debugging/E2E hooks (the props are consumed directly now). The shell wraps the painted layout in a `role="group" aria-label="<Scope> tasks"` container; inside it the list carries `data-testid="task-list"` and the board `data-testid="task-board"`, and rows/cards render as `li[data-task-id]` with `data-selected="true"`/`aria-current="true"` on the selected one.

**Depends on / Used by** — `next/navigation` (`useRouter`, `useSearchParams`), `lib/db/schema` (`TaskPriority`, `TaskStatus`), `lib/domain/tasks` (`endOfWeek`, `localToday`, `TaskScope`), `lib/domain/taskViews` (`filterTasks`, `groupTasks`, `sortTasks`), `lib/query/tasks` (`useTasks`, `useCreateTask`, `useUpdateTask`, `useDeleteTask`), `lib/query/collections` (`useCollections`), `lib/services/permissions` (`canWriteCollection`, `foldCollectionPermission`), `lib/services/preferences` (`TimeFormat`), `lib/ui/taskDeepLink`, `lib/ui/taskViewParams` (`parseTaskViewState`, `parseTaskScope`, `mergeTaskViewParams`, `mergeTaskScopeParams`, `TaskViewState`), `lib/ui/undo` (`pushUndo`), `lib/ui/undoToast`, `lib/ui/useTaskShortcuts`, `lib/ui/useUndoHotkey`, `lib/validation/tasks` (`UpdateTaskInput`), `components/ui/button`, `sonner`, and the siblings `TaskBoard`/`TaskCaptureRow`/`TaskViewTabs`/`TaskToolbar`/`TaskList`/`TaskPanel`/`TaskShortcutHelpDialog`/`types`. Rendered only by `app/(app)/tasks/page.tsx`.

**Debugging** —
- A completed/dropped/deleted task vanishes with no toast to undo it -> the settle refetch removed the row but the compensating action was not pushed (a no-op echo is skipped on purpose) -> `patchStatus`/`deleteTaskWithUndo` above.
- The toast's Undo brings back the wrong task or nothing -> the toast was shown without its own `pushUndo` handle, or the action was already undone/dropped by the 20-action cap -> `lib/ui/undo.ts`, `lib/ui/undoToast.ts`.
- Undo of a delete creates a second copy instead of restoring the old one -> intended: `deleteTask` hard-deletes, so undo re-creates the row with a **new id**; reload the list and expect the new id -> `deleteTaskWithUndo` above.
- Undo of a delete comes back with the wrong priority or status (an Urgent row returns `none`, an in-progress/done row returns `open`) -> the payload builders were inlined again (the old body sent title/notes/dates/list only) -> `lib/ui/taskUndo.ts` `deletedTaskCreateInput`/`deletedTaskRestorePatch`; the restore PATCH is skipped when it is empty.
- Undo of a move puts the task back in the list but at the end -> the second `sortOrder` PATCH was lost (a move PATCH always appends) -> `patchMove`'s undo closure.
- The panel opens blank or for the previous task -> `editorTask` is stale or `TaskPanel`'s `key={task.id}` was removed -> this file and `components/tasks/TaskPanel.tsx`.
- The panel keeps showing the pre-edit status after Complete/Drop -> `editorTask` was not refreshed from the PATCH echo (or the panel rendered the open-time snapshot instead of `panelTask`) -> this file's `patch` `onSuccess` and `panelTask`.
- Focus lands on `<body>` after the panel closes -> `closeEditor`'s timeout found neither a selected row nor a scope tab (the list re-rendered late) -> this file's `closeEditor`.
- A badge lags one step behind a row edit -> `useUpdateTask` is row-only optimistic and `counts` are recomputed on the settle refetch -> `lib/query/tasks.ts`.
- A task exists but every view is empty -> it is dated beyond this week (no triage bucket) or its list is private to the partner (server 404) -> `lib/domain/tasks.ts` `bucketOf` and `lib/services/tasks.ts` `listTasks`.
- The list is empty but the task exists and a filter badge is violet -> a status/priority/list filter is active (the URL says so) -> clear it from the toolbar or the empty state's Clear-filters button; check `state.status`/`priority`/`collectionId`.
- `?task=<id>` lands on `/tasks` with no panel -> the deep-link lookup failed (read the toast), or the param was marked handled **before** it settled: development StrictMode's setup → cleanup → setup then skips on the second pass while the first, cancelled closure holds the only response -> this file's effect plus `lib/ui/taskDeepLink.ts`.
- The panel reopens after being closed from a chip -> `closeEditor` did not remove the param, or the handled ref was cleared while the param still names the task -> this file's `clearTaskParam`.
- A chip click opens the event details instead of the task -> the calendar branch on `extendedProps.kind` was lost (see `components-calendar.md`), not this file.
- A row cannot be dragged onto the mini month, or its Undo restores the wrong date -> the row's payload and the mini-month/drop listeners disagree on the `text/x-nailong-task` shape (`{ id, dueOn }`) -> `lib/ui/taskDrag.ts`, `components/tasks/TaskRow.tsx`, `components/calendar/MiniMonth.tsx`, `lib/ui/useTaskPlanDrop.ts`.
- The due chip is red at the wrong moment (a timed deadline today that has not passed is red, or a date-only deadline shown as overdue today) -> the colour comes from the server's `TaskView.overdue`, which uses the household wall clock: a date-only deadline covers the whole day, a timed one is overdue only after its minute -> `lib/domain/tasks.ts` `isOverdue`, `lib/services/tasks.ts` `toTaskView`; the chip never compares dates locally.
- "Move to list…" is disabled or missing a list -> there is no other writable `kind="list"` collection, or `["collections"]` is still loading -> `moveTargets` above plus `GET /api/collections`.
- `j`/`k`/`1`/`x`/`z` do nothing -> focus is in an input, a dialog/menu is open, or `shortcutsEnabled` is off (`z` is not gated: `useUndoHotkey` is unconditional like the calendar's) -> check `lib/ui/useTaskShortcuts.ts`, `lib/ui/useUndoHotkey.ts` and `[data-testid="tasks-shell"]`'s `data-shortcuts-enabled`.
- `j` moves the wrong row after switching scopes -> the scope change should have cleared `selectedTaskId`; if it did not, `changeScope` lost the reset -> this file.
- The next triage key silently does nothing after a row was completed/deleted -> the task left the visible rows on the settle refetch and a stale `selectedTaskId` survived; the selection-coherence effect should have moved the selection to the nearest surviving row and focused it -> this file's `previousTasksRef` effect, `data-selected` on the rows.
- Focus lands on the scope tab after the last visible row disappears -> intended: there is no row to focus, and the tab is a real keyboard stop so `j` still means "next row" -> this file's `activeRef`.
- Pressing `1` twice leaves the task in Today with no visible change -> the PATCH is the same date, so the server echoes it and no undo toast appears -> this is the no-op guard, not a bug.
- Choosing Board still shows a grouped list -> `state.layout` is not `"board"` (the URL says `layout=board`), or the shell's conditional render lost the `TaskBoard` branch -> this file's render plus `components/tasks/TaskBoard.tsx`.
- The board shows no Done/Dropped columns -> intended: the server omits closed rows unless "show closed" (`closed=1`) is on -> the toolbar's Hide-closed toggle, `lib/query/tasks.ts`.
- The toolbar change is lost on reload -> `updateState` did not run `router.replace` (or `mergeTaskViewParams` dropped the key because it equalled the default) -> this file's `updateState` plus `lib/ui/taskViewParams.ts`.
- A row action does nothing and no toast appears -> the click landed before hydration on the E2E dev server, or the list is view-only for the partner (the PATCH 403s and toasts) -> rerun the action and read the toast.
- The breadcrumb on `/tasks` says "Calendar" -> the route lost its live roadmap entry: `ROUTE_CRUMBS` is built from `LIVE_ENTRIES`, so an unlisted `(app)` route falls back -> `lib/roadmap.ts`, `components/shell/AppShell.tsx`.
- The page scrolls the whole document -> a wrapper added `h-screen`/`overflow-hidden`; only `main` may scroll -> viewport contract in `app-routes.md` (`app/(app)/layout.tsx`).

**Tests** — `tests/e2e/tasks.spec.ts` is the UI gate (the v0.2.1 rewrite covers the grouped list, board, inline status/priority, toolbar/sort/filter, panel open/close, deep link, keyboard triage, sidebar quick add and partner privacy). ### components/tasks/TaskShortcutHelpDialog.tsx

**Purpose** — The `/tasks` `?` sheet: one "Global" group (`Shift+K`, `?`; `/` is the calendar's search and is not bound on `/tasks`, so it is deliberately absent) and one "Triage" group (`j`/`k`, `1`–`4`, `x`, `Enter`, `Escape`), listing `3` as "Someday: clear the due date and time" and `1`/`2` as "Set the due date to today / to the end of this week", `j`/`k` as "Next/previous task or card" and `x` as "Complete the selected task or card". A closing note explains the board: `j`/`k` move through the cards in column order, `x` completes the selected card, a card's menu or a drag between columns changes its status, and there is no within-column reorder. It is deliberately separate from `components/calendar/ShortcutHelpDialog.tsx` because `j`/`k` mean row/card selection here and period navigation there.

**Public API** — `export function TaskShortcutHelpDialog(props: { open: boolean; onClose: () => void })`. Rows live in a module-level `GROUPS` constant; there are no queries or mutations.

**State & side effects** — Stateless/controlled. Renders the shared `Dialog`/`DialogContent` (`title="Keyboard shortcuts"`, description "Single-key shortcuts can be turned off in Settings → Calendar."), so Radix owns Escape, outside-click, focus trap and focus return to the opening control. `onOpenChange(false)` calls `onClose`; the footer "Close" button does too. Opened by `?` or the "Keyboard shortcuts" button beside the scope tabs in `TasksShell`. The `Enter` row reads "Open the selected task in the panel", because that is what the shell's `openSelection` does (Task 13 replaced the modal editor with `TaskPanel`); the board note under the two groups is plain copy, not a key row, so it can never advertise a gesture `resolveTaskShortcut` does not own.

**Depends on / Used by** — `components/ui/dialog`, `components/ui/button`. Rendered by `components/tasks/TasksShell.tsx`.

**Debugging**
- `?` opens the calendar sheet instead of this one -> focus is on `/`, not `/tasks`; both hooks are page-scoped -> the calendar's `ShortcutHelpDialog` is the other mount.
- `?` does nothing while the sheet is open -> expected: `hasOpenOverlay()` blocks all page keys and Radix owns Escape/close.
- A key advertised here does not work -> compare `GROUPS` with `resolveTaskShortcut` in `lib/ui/useTaskShortcuts.ts`; the dialog must not advertise a gesture the resolver does not own.

**Tests** — No direct unit test (static markup); the triage tests in `tests/e2e/tasks.spec.ts` exercise a subset of the keys it lists (selection, triage and the panel hand-off), not all 12.

### components/tasks/TaskRow.tsx

**Purpose** — One dense ClickUp-style row: completion checkbox, a clickable title (struck through when done), the owning list's shade dot and name, the inline `TaskStatusPill`/`TaskPriorityFlag`/`TaskDueChip`, and the overflow menu with `Open`, `Move to list…`, `Drop` and `Delete`. It remains the triage layer's selection unit and the drag source.

**Public API** — `export function TaskRow(props: { task: TaskView; today: string; timeFormat: TimeFormat; timezone: string; selected: boolean; onFocus(): void; actions: TaskActions; moveTargets: WritableList[] })`. `actions` is built per task by `TasksShell.actionsFor` (via `TaskList.actionsFor`), so every control changes its own row; `moveTargets` arrives with the current list already filtered out, and `timeFormat`/`timezone` are the household 12/24-hour preference and zone forwarded to the due chip (the zone feeds the shared time picker's "now" marker).

**State & side effects** — No local state of its own (the dropdown and the due popover own their open state; `TaskDueChip` owns the picker). The `<li>` is `tabIndex={0}`, `aria-label={task.title}`, carries `data-task-id={task.id}`, `data-selected="true"` and `aria-current="true"` while selected (`bg-violet-soft` plus a 2px violet inset shadow), and reports focus upward through `onFocus` so a click/Tab on any control selects the row. It is `draggable`: `onDragStart` calls `setTaskDragPayload(event.dataTransfer, task)` from `lib/ui/taskDrag.ts`, which stamps `text/x-nailong-task` with the id and current `dueOn` and sets `effectAllowed = "move"`. The title is a real `<button>` whose click calls `actions.onOpen` (so `Enter` on it activates natively instead of being swallowed by the shortcut layer); its text gets `line-through` when `status === "done"`. The checkbox's accessible name is exactly the task title (`Checkbox label={task.title}`) and calls `actions.onToggleDone`, which the shell turns into `done`/`open`. ### components/tasks/TaskDueChip.tsx

**Purpose** — The task's only date control: one chip reading `Tue 27 Oct` (or `Tue 27 Oct, 18:00` when a time is set, and just the calendar icon when the task is undated) that opens a Radix popover holding the shared `MiniMonth` plus the calendar's own `TimeField` for the optional due time, `Clear due date` and `Done`. It replaces the two-chip `TaskDateChips` (a scheduled date and a due date) that the single-deadline model retired.

**Public API** — `export function TaskDueChip(props: { dueOn: string | null; dueTime: string | null; overdue: boolean; today: string; title: string; timeFormat: TimeFormat; timezone: string; onChange: (patch: { dueOn?: string | null; dueTime?: string | null }) => void })`. The chip trigger is `data-testid="task-due"`; the footer buttons are `task-due-clear` ("Clear due date") and `task-due-done` ("Done"). The time control is the shared `TimeField`: its trigger carries `time-field-trigger` (and the picker `time-field-popover`/`time-field-selected`/`time-field-clear`), and its accessible name is `Due time for <title>` (list `Due time for <title> quick pick`) — there is no task-specific time-input test id. The chip's accessible name is `Set due date for <title>` while undated and `Due date for <title>: <date>[, <time>]` once set. The compact label comes from `formatShortWallDate(dueOn, today)` (the year appears only when it differs from the household's current year) and `formatWallTime(dueTime, timeFormat)` renders the time in the household 12/24-hour preference.

**State & side effects** — Local `open` only; the embedded `TimeField` owns its own typed-draft/error/flash state. The picker is keyed by `dueOn` and anchored on the saved date (else `today`), and picking a day calls `onChange({ dueOn: date })` **without closing**, so the time can be set in the same visit. The optional time is the calendar's shared `TimeField` below the mini month: `value={dueTime}`, `onChange` → `onChange({ dueTime })`, `onClear` → `onChange({ dueTime: null })`, `timezone` for its "now" marker. Picking a 15-minute row or committing typed text applies immediately as one PATCH and closes only the time list; "Clear time" drops the time while keeping the date; the trigger shows `No time`, or `Set a date first` while `dueOn` is null — in that state the trigger is also `disabled`, because a time needs a date. `Clear due date` (disabled while undated) sends `{ dueOn: null, dueTime: null }` and closes the whole popover; `Done` only closes it; Escape/outside-click cancel. No query and no storage: the shell owns the single PATCH, its toast and targeted undo. `overdue` is the **server** flag (`TaskView.overdue`, computed against the household wall clock); the chip only paints `font-bold text-danger-ink`, so the device clock never decides the colour.

**Depends on / Used by** — `@radix-ui/react-popover`, `components/calendar/DatePickerPopover` (the shared mini-month popover body), `components/calendar/TimeField` (the same slot picker the event dialog uses, with its `timeSlots` parser), `components/ui/button`, `components/ui/icons` (`CalendarIcon`), `lib/services/preferences` (`TimeFormat`), `lib/time/format` (`formatShortWallDate`, `formatWallTime`), `lib/utils` (`cn`). Rendered by `components/tasks/TaskRow.tsx`, `TaskBoardCard.tsx` and `TaskPanel.tsx`, each forwarding the shell's `timeFormat` **and** `timezone` (the latter feeds the time picker's "now" marker); the patch goes through `TasksShell`'s `onDue` (`patchDue`).

**Debugging**
- The chip shows a long `Wed, 28 Oct 2026` instead of `Tue 27 Oct` -> the caller used `formatWallDate`; the chip needs `formatShortWallDate(dueOn, today)` -> this file.
- The chip is red on a task that is due today -> only an active **timed** deadline earlier than the household wall clock is overdue today; a date-only deadline covers the whole day and a done/dropped row is never overdue. Check the API's `TaskView.overdue` instead of a local date comparison -> `lib/domain/tasks.ts` `isOverdue`, `lib/services/tasks.ts` `toTaskView`.
- The time trigger is disabled or reads "Set a date first" -> intended: a time needs a date; pick a day first (the date pick must PATCH and keep the due popover open) -> this file's `DatePickerPopover.onPick`.
- The time list's "now" marker sits on the wrong row -> `timezone` was not forwarded through `TasksShell → TaskList`/`TaskBoard`/`TaskPanel → TaskRow`/`TaskBoardCard` -> those props plus `components/calendar/TimeField.tsx`.
- A typed time is rejected although it looks valid -> `parseTypedTime` is format-aware: a 24-hour household rejects an am/pm suffix such as `8:37 PM` instead of guessing -> the `timeFormat` prop plus `components/calendar/TimeField.tsx` and `timeSlots.ts`.
- "Clear time" removes the date, or "Clear due date" leaves the time behind -> the two actions are deliberately separate (`TimeField.onClear` clears only `dueTime`; the chip's footer button clears both), and the service also nulls the time whenever the date clears -> this file plus `lib/services/tasks.ts` `updateTask`.
- Escape closes the whole task panel instead of just the due popover -> the popover content must stay the topmost Radix `DismissableLayer` (portalled inside its own root) and the panel's capture listener must bail on `[data-radix-popper-content-wrapper]` -> this file's `PopoverPrimitive.Portal`, `TaskPanel.tsx`.

**Tests** — No direct unit test (the repo has no React renderer) and no e2e drives the chip itself after the v0.2.1 rewrite; the embedded `TimeField` is covered by `tests/unit/timeSlots.test.ts` (parser/slot grid) and `tests/e2e/event-fields.spec.ts`, and the mini month by `tests/e2e/mini-month.spec.ts`. The patch rules behind it (clearing the date clears the time; a time without a date is 400) are covered by `tests/unit/task-cache.test.ts`, `tests/integration/tasks.test.ts` and `tests/integration/tasks-api.test.ts`.

**Public API** — `export function TaskCaptureRow(props: { timezone: string; collectionId?: string; status?: TaskStatus; placeholder?: string; ariaLabel?: string; inputId?: string; onCaptured?: (task: TaskView) => void })`. `timezone` drives `localToday`; `collectionId` files the task in that list; `status` is the board column's status and is sent **in the create body** (only `open`/`in_progress` are accepted; any closed value is ignored); `ariaLabel` is the `sr-only` label (`Add a task` by default; the board passes `Add a task to <Status>` so its per-column inputs are distinguishable); `inputId` defaults to `"task-capture"` and is the DOM id, the test id and the label target — the board passes `task-capture-<status>` so its columns do not duplicate the globals.
