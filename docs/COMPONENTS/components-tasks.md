# Tasks workspace components

The `/tasks` triage workspace: capture, the four buckets and the row actions.
Bucketing itself is server-side (`lib/domain/tasks.ts`, `lib/services/tasks.ts`);
these components choose a view, render what the server returns and turn row
actions into PATCH/DELETE calls. The page-scoped keyboard triage layer
(`lib/ui/useTaskShortcuts.ts`, mounted by `TasksShell`) and the global `Shift+K`
capture live alongside them; `GlobalCapture` itself is documented in
[`components-shell-and-sidebar.md`](components-shell-and-sidebar.md), because
`AppShell` mounts it on every route.

`app/(app)/tasks/page.tsx` is documented in
[`app-routes.md`](app-routes.md#appapptaskspagetsx) — the repo rule is one
`###` section per file, and every `app/` route lives in `app-routes.md`, so the
page cannot appear here as well.

**Read this when** a row action does nothing, a task shows in the "wrong"
bucket, a touch target is too small, or an E2E spec cannot find a control: the
accessible-name patterns are listed per component below.

### components/tasks/TasksShell.tsx

**Purpose** — The client workspace under the server page: capture bar, view switcher, the active bucket's rows with their loading, error and empty states, the task editor and the page-scoped keyboard triage/undo layers. It is the only owner of the selected view, the row selection, the open editor and the task/collection mutations.

**Public API** — `export function TasksShell(props: { timezone: string; weekStartsOn: 0 | 1; shortcutsEnabled: boolean; currentUserId: string })`. No other exports. It mounts `TaskEditorDialog` itself (opened by `Enter`, the row's "Edit task…" action, and the `?task=<id>` deep link from a calendar chip) — the Task 9 `onOpenTask` hand-off prop was replaced by the real editor.

**State & side effects** — Local `view` (`useState<TaskBucket>`, default `"inbox"`), `selectedTaskId: string | null`, `editorTask: TaskView | null` (the editor's snapshot; `null` means closed) and `helpOpen`. Queries: `useTasks(view)` over the key `["tasks", view ?? "all", collectionId ?? null]` (`/api/tasks?view=…`, returns `{ tasks, counts }`) and `useCollections()` (`["collections"]`, needed for the Move-to-list submenu). `counts` stays `undefined` until the first payload (loading and error render no badges) and `today` is `useMemo(() => localToday(timezone), [timezone])`; bucket membership itself is never recomputed here. Mutations: `useUpdateTask` for complete/uncomplete (`status`), Plan and the `1`/`2`/`3` keys (`scheduledOn`/`dueOn`; `3` may also move an undated Inbox row), the editor save (`title`, `notes`, `checklist`), Move, the `4` key and `3`'s Inbox filing (`collectionId` + `sortOrder` on undo) and Drop (`status: "dropped"`); `useDeleteTask` for Delete and `useCreateTask` for the delete-undo re-create. Failures toast by path: complete, reopen and Drop all go through the same status patch, so they share `Could not update the task.`; Plan and the `1`/`2`/`3` clear-dates path toast `Could not schedule the task.`, Move/`4`/`3`'s Inbox filing `Could not move the task.`, and Delete `Could not delete the task.`; `4` with no other writable list toasts `No other writable list to move to.`, while `3` toasts `Filed to Someday` on a successful Inbox filing, `Already unscheduled` when the Inbox has no other writable list, and `Already in Someday` for an undated row outside the Inbox. There is no optimistic create or delete (only the PATCH hook is optimistic, and the settle refetch removes completed/dropped rows). `useUndoHotkey()` is mounted here, so `z`/`Ctrl+Z` work on `/tasks` exactly as on the calendar. Move targets are the viewer's writable lists, computed here with `canWriteCollection` over `foldCollectionPermission` (the shared root/child fold, also used by the sidebar) and labelled `Parent / Child` for sub-lists; the current list is filtered per row and the server stays authoritative (a stale tree gets a 403).

**`?task=` deep link** — A calendar task chip pushes `/tasks?task=<id>`. `TasksShell` reads `useSearchParams()`; the param is one-shot, and the handled marker is set by `deepLinkHandledRef` **only once the lookup settles** (`lib/ui/taskDeepLink.ts`). That ordering is required, not stylistic: `next.config.ts` sets `reactStrictMode: true`, so development runs the effect's setup → cleanup → setup, the first `GET /api/tasks/{id}` closure is cancelled before its response, and an early marker would make the second setup return while that cancelled closure owns the only answer — no editor would ever open. The in-flight promise is therefore cached in a ref keyed by the param, so the second setup awaits the same request and the marker is set at the settle site. The effect prefers the row from the current view (through `tasksRef`, so arriving rows do not re-run it) and otherwise uses the `GET`; a scheduled chip task is never in the Inbox view, so the `GET` is the normal path, not a fallback. A 404/403 toasts and replaces the URL with `/tasks`. `closeEditor()` (Cancel, Escape, Save, Delete) clears the param with `router.replace("/tasks")` before restoring focus, so a reload or Back does not reopen a dismissed dialog. Observable behaviour of the chip route: `/tasks` carries no view parameter and `TasksShell`'s `view` is local state defaulting to `"inbox"`, so arriving from the calendar mounts the shell on the Inbox; clearing the param on close is a same-route replace and only removes `?task=` (the current view is not reset by it — there is no view in the URL to restore either way).

**Undo contract (targeted)** — Every successful complete/reopen/drop/delete/schedule/move calls `pushUndo` with a compensating action and shows `undoToast(message, handle)` (`lib/ui/undoToast.ts`), so the toast's Undo reverts *that* action and not whatever landed last. The stack labels are `Complete task` / `Reopen task` / `Drop task` / `Delete task` / `Schedule task` / `Move task`; `z`/`Ctrl+Z` still consume the shared stack LIFO. A PATCH whose server echo equals the previous row (status or both dates, or the same collection) pushes **no** action — the toast would be a lie.

| Action | Undo (compensating request) |
|---|---|
| Complete / reopen / drop | one PATCH back to the previous `status` |
| Plan pick, `1`/`2`, `3`'s clear-dates | one PATCH restoring the previous `scheduledOn` + `dueOn` |
| Move (menu, `4`, `3`'s Inbox filing) | PATCH `collectionId` back to the source list, then PATCH `sortOrder` (a move always appends, so the position needs the second request) |
| Delete | `POST /api/tasks` with the captured `title`/`notes`/dates/`collectionId`, then PATCH `checklist` + `sortOrder`; the re-created task gets a **new id** (there is no trash table) |
| Editor save | **no** undo: the editor is a deliberate whole-form save; delete is the undoable action there |

**Selection and the shortcut contract** — `useTaskShortcuts(shortcutsEnabled, …)` is mounted here, so every key is page-scoped and inert when the preference is off. `j`/`k` clamp through the current view's `tasks` (from no selection `j` lands on the first row and `k` on the last), set `selectedTaskId` and call the row's `focus()`; clicking or tabbing into a row selects it through `TaskRow.onFocus`. `1` sets `scheduledOn = localToday(timezone)`, `2` sets `scheduledOn = endOfWeek(today, weekStartsOn)` (on the household week's last day this equals today, so the task shows in Today per D6), `3` clears both dates — but an Inbox task is already undated, so there it files the row into the next writable `kind="list"` collection (the same path as `4`) and toasts `Filed to Someday`, toasts `Already unscheduled` when no other writable list exists, and toasts `Already in Someday` for an undated row outside the Inbox — `4` cycles to the next writable `kind="list"` collection, `x` PATCHes `status: "done"`, `Enter` opens `TaskEditorDialog` for the selection, `?` opens `TaskShortcutHelpDialog` (also reachable from the "Keyboard shortcuts" button beside the switcher) and `Escape` clears the selection. Changing the view clears the selection. All keys share `isTextEntryTarget`/`hasOpenOverlay`, so typing in the capture field or any open dialog/menu/popover never moves the selection; `Enter` on a focused button (checkbox, Plan, Options, switcher) is left to that control instead of the editor.

**Selection coherence** — Complete, drop, delete, Plan and Move all remove the row from the open view once the settle refetch paints. A `useEffect` over the rendered `tasks` compares the selection against the new list using `previousTasksRef` (the last rendered rows): when the selected id no longer exists, the stale id is cleared and the selection moves to the row that took its place (`min(oldIndex, length − 1)`, falling back to the first row) and that row is focused, because focus follows selection. When the view is now empty, focus goes to the current view's switcher button (`TaskViewSwitcher.activeRef`) — not the capture input, which would swallow `j` as typed text. While the editor is open the selection still moves (the modal owns focus) and `closeEditor` focuses the live selection on the next paint, falling back to the switcher. The effect never runs while the query is pending or on a view switch (the selection is null then), so a following `j`/`x`/`1` acts on a real row instead of silently no-opping on a vanished id.

**Editor wiring** — `openTask(task)` selects the row and sets `editorTask`; `closeEditor` clears it (and the `?task=` param when present) and restores focus to `li[data-selected="true"]` (or the switcher when the save re-bucketed the last row out of the view). The editor's Delete closes the dialog and then runs the same `deleteTaskWithUndo` as the row menu, so both paths push the same undo.

**Task chips are tasks, not events** — On the calendar (`/`), `CalendarShell` draws scheduled **active** tasks (`isActiveStatus`: open or in_progress) through `components/calendar/taskChip.ts` as read-only all-day FullCalendar events with ids `task:<id>` and `extendedProps.kind = "task"`. Chips join the same `events` array as the event occurrences: they inherit the grid's stacking, `dayMaxEventRows`/`eventMaxStack` and the built-in "+N more", so a day full of chips folds exactly like a day full of events. A click is branched in `CalendarShell.handleEventClick` to `router.push("/tasks?task=<id>")` — never the event details popover, event edit form, drag or resize. `data-task-id` and `aria-label="Task: <title>"` are set by `CalendarView.eventDidMount`. Rendering is read-only: a task chip's only interaction is the deep link; planning happens through the row's Plan popover or by dragging the row. Only active (`open`/`in_progress`) rows draw, so the optimistic task cache holding a just-completed/dropped row for a beat cannot paint a chip for finished work — and an in-progress task is not flagged `completed`. **Accepted superset (controller ruling):** because a chip is an all-day event on the one shared `events` array, it also appears in the Week, Day and List views; those grids are read-only for chips too (no drag/resize, click = task editor), and only the month day cells attach task-drop listeners.

States: `isError` renders `role="alert"` with "Could not load the tasks." and a "Try again" retry button; `isPending` renders `role="status"` "Loading tasks…"; zero rows renders exactly "Nothing here. Enjoy the quiet.". The root `<section aria-label="Tasks" data-testid="tasks-shell">` also carries `data-week-starts-on` and `data-shortcuts-enabled` as debugging/E2E hooks (the props are consumed directly now). Rows render as `li[data-task-id]` with `data-selected="true"`/`aria-current="true"` on the selected row.

**Depends on / Used by** — `next/navigation` (`useRouter`, `useSearchParams`), `lib/db/schema` (`TaskStatus`), `lib/domain/tasks` (`endOfWeek`, `localToday`, `TaskBucket`), `lib/query/tasks` (`useTasks`, `useCreateTask`, `useUpdateTask`, `useDeleteTask`), `lib/query/collections` (`useCollections`), `lib/services/permissions` (`canWriteCollection`, `foldCollectionPermission`), `lib/ui/undo` (`pushUndo`), `lib/ui/undoToast`, `lib/ui/useTaskShortcuts`, `lib/ui/useUndoHotkey`, `lib/validation/tasks` (`UpdateTaskInput`), `components/ui/button`, `sonner`, and the sibling `TaskCaptureBar`/`TaskEditorDialog`/`TaskRow`/`TaskShortcutHelpDialog`/`TaskViewSwitcher`. Rendered only by `app/(app)/tasks/page.tsx`.

**Debugging** —
- A completed/dropped/deleted task vanishes with no toast to undo it -> the settle refetch removed the row but the compensating action was not pushed (a no-op echo is skipped on purpose) -> `patchStatus`/`deleteTaskWithUndo` above.
- The toast's Undo brings back the wrong task or nothing -> the toast was shown without its own `pushUndo` handle, or the action was already undone/dropped by the 20-action cap -> `lib/ui/undo.ts`, `lib/ui/undoToast.ts`.
- Undo of a delete creates a second copy instead of restoring the old one -> intended: `deleteTask` hard-deletes, so undo re-creates the row with a **new id**; reload the list and expect the new id -> `deleteTaskWithUndo` above.
- Undo of a move puts the task back in the list but at the end -> the second `sortOrder` PATCH was lost (a move PATCH always appends) -> `patchMove`'s undo closure.
- The editor opens blank or for the previous task -> `editorTask` is stale or `TaskEditorDialog`'s `key={task.id}` was removed -> this file and `components/tasks/TaskEditorDialog.tsx`.
- Focus lands on `<body>` after the editor closes -> `closeEditor`'s timeout found neither a selected row nor the switcher (the list re-rendered late) -> this file's `closeEditor`.
- A badge lags one step behind a row edit -> `useUpdateTask` is row-only optimistic and `counts` are recomputed on the settle refetch -> `lib/query/tasks.ts`.
- A task exists but every view is empty -> it is dated beyond this week (no triage bucket) or its list is private to the partner (server 404) -> `lib/domain/tasks.ts` `bucketOf` and `lib/services/tasks.ts` `listTasks`.
- `?task=<id>` lands on `/tasks` with no editor -> the deep-link lookup failed (read the toast), or the param was marked handled **before** it settled: development StrictMode's setup → cleanup → setup then skips on the second pass while the first, cancelled closure holds the only response -> this file's effect plus `lib/ui/taskDeepLink.ts`.
- The editor reopens after being closed from a chip -> `closeEditor` did not `router.replace("/tasks")`, or the handled ref was cleared while the param still names the task -> this file.
- A chip click opens the event details instead of the task -> the calendar branch on `extendedProps.kind` was lost (see `components-calendar.md`), not this file.
- A row cannot be dragged onto the mini month, or its Undo restores the wrong date -> the row's payload and the mini-month/drop listeners disagree on the `text/x-nailong-task` shape (`{ id, scheduledOn }`) -> `lib/ui/taskDrag.ts`, `components/tasks/TaskRow.tsx`, `components/calendar/MiniMonth.tsx`, `lib/ui/useTaskPlanDrop.ts`.
- "Move to list…" is disabled or missing a list -> there is no other writable `kind="list"` collection, or `["collections"]` is still loading -> `moveTargets` above plus `GET /api/collections`.
- `j`/`k`/`1`/`x`/`z` do nothing -> focus is in an input, a dialog/menu is open, or `shortcutsEnabled` is off (`z` is not gated: `useUndoHotkey` is unconditional like the calendar's) -> check `lib/ui/useTaskShortcuts.ts`, `lib/ui/useUndoHotkey.ts` and `[data-testid="tasks-shell"]`'s `data-shortcuts-enabled`.
- `j` moves the wrong row after switching views -> the view change should have cleared `selectedTaskId`; if it did not, `changeView` lost the reset -> this file.
- The next triage key silently does nothing after a row was completed/deleted -> the task left the view on the settle refetch and a stale `selectedTaskId` survived; the selection-coherence effect should have moved the selection to the nearest surviving row and focused it -> this file's `previousTasksRef` effect, `data-selected` on the rows.
- Focus lands on the view switcher after the last row in the view disappears -> intended: there is no row to focus, and the switcher is a real keyboard stop so `j` still means "next row" -> this file's `activeRef`.
- Pressing `1` twice leaves the task in Today with no visible change -> the PATCH is the same date, so the server echoes it and no undo toast appears -> this is the no-op guard, not a bug.
- A row action does nothing and no toast appears -> the click landed before hydration on the E2E dev server, or the list is view-only for the partner (the PATCH 403s and toasts) -> rerun the action and read the toast.
- The breadcrumb on `/tasks` says "Calendar" -> the route lost its live roadmap entry: `ROUTE_CRUMBS` is built from `LIVE_ENTRIES`, so an unlisted `(app)` route falls back -> `lib/roadmap.ts`, `components/shell/AppShell.tsx`.
- The page scrolls the whole document -> a wrapper added `h-screen`/`overflow-hidden`; only `main` may scroll -> viewport contract in `app-routes.md` (`app/(app)/layout.tsx`).

**Tests** — `tests/e2e/tasks.spec.ts` (scenario 2: global `Shift+K` capture, keyboard-only `j`/`k` selection, `1` scheduling, `x` completion, `3` filing an undated Inbox task to Someday with the `Filed to Someday` toast and the `Already in Someday` follow-up, and the targeted toast Undo for two captures, which hovers the front toast first so Sonner expands the collapsed stack before the older toast's Undo is clicked; the editor-persistence test: open a row with `Enter` and once through the row menu's `Edit task…`, the due-date set (Inbox → Today, badge painted) and clear (back to Inbox, badge gone) plus Escape-without-saving; scenario 4: complete via `x`, counts drop, toast Undo returns the task exactly once and restores the counts; the delete-undo test: delete from the row menu, toast Undo re-creates the task with a new id but the same title, owning list and checklist, and a second undo request does not duplicate it; scenario 3: drag the row onto the sidebar mini-month's today (`dragTo` with `steps` so a `dragover` is synthesized and the drop highlight path runs), assert `scheduledOn` and the Today row, click the `Task planned` toast's Undo and assert via `GET /api/tasks/{id}` that `scheduledOn` returns to `null` exactly once (Sonner consumes the toast, so the second attempt is `z` and must be a no-op), Plan it to another quiet day, assert the month-grid chip on that day and that clicking the chip opens `/tasks?task=<id>` with the editor, then closing clears the param). ### components/tasks/TaskShortcutHelpDialog.tsx

**Purpose** — The `/tasks` `?` sheet: one "Global" group (`Shift+K`, `?`; `/` is the calendar's search and is not bound on `/tasks`, so it is deliberately absent) and one "Triage" group (`j`/`k`, `1`–`4`, `x`, `Enter`, `Escape`), listing `3` as "Someday: clear dates, or file an Inbox task to a list". It is deliberately separate from `components/calendar/ShortcutHelpDialog.tsx` because `j`/`k` mean row selection here and period navigation there.

**Public API** — `export function TaskShortcutHelpDialog(props: { open: boolean; onClose: () => void })`. Rows live in a module-level `GROUPS` constant; there are no queries or mutations.

**State & side effects** — Stateless/controlled. Renders the shared `Dialog`/`DialogContent` (`title="Keyboard shortcuts"`, description "Single-key shortcuts can be turned off in Settings → Calendar."), so Radix owns Escape, outside-click, focus trap and focus return to the opening control. `onOpenChange(false)` calls `onClose`; the footer "Close" button does too. Opened by `?` or the "Keyboard shortcuts" button beside the view switcher in `TasksShell`.

**Depends on / Used by** — `components/ui/dialog`, `components/ui/button`. Rendered by `components/tasks/TasksShell.tsx`.

**Debugging**
- `?` opens the calendar sheet instead of this one -> focus is on `/`, not `/tasks`; both hooks are page-scoped -> the calendar's `ShortcutHelpDialog` is the other mount.
- `?` does nothing while the sheet is open -> expected: `hasOpenOverlay()` blocks all page keys and Radix owns Escape/close.
- A key advertised here does not work -> compare `GROUPS` with `resolveTaskShortcut` in `lib/ui/useTaskShortcuts.ts`; the dialog must not advertise a gesture the resolver does not own.

**Tests** — No direct unit test (static markup); scenario 2 of `tests/e2e/tasks.spec.ts` exercises the keys it lists.

### components/tasks/TaskCaptureBar.tsx

**Purpose** — One always-visible input for fast task capture: `Enter` files the task in the Inbox, `Shift+Enter` schedules it for the household's today.

**Public API** — `export function TaskCaptureBar(props: { timezone: string; onCaptured?: (task: TaskView) => void })`. The `timezone` prop is required for `localToday(timezone)` and is the one addition to the plan's `{ onCaptured? }` signature.

**State & side effects** — Local `title` only. `useCreateTask()` (`POST /api/tasks`, then invalidates `["tasks"]`). The input has `id="task-capture"`, `type="text"`, placeholder exactly `Add a task…`, an `sr-only` `<label htmlFor="task-capture">Add a task</label>` and a hint line (`id="task-capture-hint"`, wired with `aria-describedby`) "Enter adds to Inbox · Shift+Enter schedules it for today". `onKeyDown` intercepts `Enter` only (`preventDefault`), passing `event.shiftKey` to the mutation: `{ title }` or `{ title, scheduledOn: localToday(timezone) }`. The title is trimmed; an empty/whitespace title is ignored. The input is `disabled` while the mutation is pending; the text is cleared and `onCaptured` fired only on success, so a failure keeps the text and toasts `Could not add the task.`. No local storage. `TasksShell` does not pass `onCaptured` yet: it is the hook the later focus/announce wiring uses.

**Depends on / Used by** — `lib/domain/tasks` (`localToday`), `lib/query/tasks` (`useCreateTask`), `lib/services/tasks` (`TaskView`), `sonner`. Rendered by `TasksShell`. The E2E spec drives it through `#task-capture` and `page.keyboard.press("Enter")`.

**Debugging** —
- Typing and pressing Enter does nothing -> the title was blank after trimming, or a request is still in flight (the input is disabled) -> this file's `capture`.
- Shift+Enter files the task in Inbox instead of Today -> `event.shiftKey` was not forwarded, or the household zone is wrong so "today" is another date -> check `capture` and `household.timezone`.
- The typed text disappears after a server error -> `setTitle("")` moved into `onError` or outside `onSuccess` -> `capture`'s callbacks.

**Tests** — `tests/e2e/tasks.spec.ts` (all three captures; persistence after reload).

### components/tasks/TaskViewSwitcher.tsx

**Purpose** — The segmented Inbox · Today · Week · Someday control with each bucket's open count, plus the cross-cutting overdue badge.

**Public API** — `export const TASK_BUCKET_LABELS: Record<TaskBucket, string>` (also imported by `TasksShell` for the row list's label); `export function TaskViewSwitcher(props: { view: TaskBucket; counts?: TaskCounts; onChange: (view: TaskBucket) => void; activeRef?: Ref<HTMLButtonElement> })`. `activeRef` is set on the current view's button so an emptied view can hand focus back here.

**State & side effects** — Stateless and controlled; the selected view lives in `TasksShell` (default Inbox). Buttons render in `TASK_BUCKETS` order, each with `aria-pressed={view === bucket}` and, once counts have loaded, `aria-label` `"<Label>, <count> open"` (for example `Today, 3 open`); before the first payload (loading or error) `counts` is `undefined`, every button still renders, its accessible name is just the label, and no badge is drawn — the switcher never shows a false row of zeros. The visible count is an `aria-hidden` badge with `data-testid="tasks-count-<bucket>"`; once counts exist a zero still renders as `0`. `counts.overdue > 0` renders one separate badge (`data-testid="tasks-overdue-count"`, danger colours, text `N overdue`) and nothing when zero: overdue is deliberately **not** a fifth bucket, because an overdue task can sit in Today or Week. No query, no storage.

**Depends on / Used by** — `lib/domain/tasks` (`TASK_BUCKETS`, `TaskBucket`), `lib/services/tasks` (`TaskCounts`), `lib/utils` (`cn`). Rendered by `TasksShell`.

**Debugging** —
- A count looks wrong but the rows look right -> `counts` is global across every visible active task, even when the rows are filtered -> `GET /api/tasks` returns global counts (documented in `app-routes.md`).
- The overdue badge disappears while a due date is in the past -> the task is done/dropped (no longer active) or `dueOn === today` (not overdue) -> `isOverdue` in `lib/domain/tasks.ts`.
- `getByRole("button", { name: "Today" })` matches two controls -> the popover's Today shortcut and this bucket both exist; this one's name is `Today, N open` -> scope the locator.

**Tests** — `tests/e2e/tasks.spec.ts` asserts the bucket rows and the count badges after reload.

### components/tasks/TaskRow.tsx

**Purpose** — One row: accessible completion checkbox, title (struck through when done), due badge, the owning list's shade dot, the Plan popover and the row menu with `Edit task…`, `Move to list…`, `Drop` and `Delete`.

**Public API** — `export function TaskRow(props: { task: TaskView; today: string; selected: boolean; onFocus: () => void; moveTargets: ReadonlyArray<{ id: string; name: string }>; onToggleDone: (done: boolean) => void; onPlan: (date: string | null) => void; onMove: (collectionId: string) => void; onDrop: () => void; onEdit: () => void; onDelete: () => void })`. All state lives in the shell; the row only renders and calls back.

**State & side effects** — No local state besides the Plan popover's open flag (inside `TaskPlanPopover`). The `<li>` is `tabIndex={0}`, `aria-label={task.title}`, carries `data-task-id={task.id}`, `data-selected="true"` and `aria-current="true"` while selected (plus a `bg-well` background), and reports focus upward through `onFocus` so a click/Tab selects it. It is `draggable`: `onDragStart` calls `setTaskDragPayload(event.dataTransfer, task.id)` from `lib/ui/taskDrag.ts`, which stamps `text/x-nailong-task` with the task id and sets `effectAllowed = "move"`; the full month grid's day cells and the sidebar mini month are the drop targets that read it. The checkbox's accessible name is exactly the task title (`Checkbox label={task.title}`); checking PATCHes `status: "done"`, unchecking `status: "open"`. The title gets `line-through` when `status === "done"` (visible only while the optimistic row survives; done rows are not listed after the settle refetch). A due date renders a badge: `Overdue` in `bg-danger-soft`/`text-danger-ink` when `isOverdue(task, today)`, otherwise `formatWallDate(dueOn)` in the neutral well style; no due date renders no badge. The collection dot is `shadeTokens(collection.hueFamily, collection.shadeIndex).main` when the hue is a known family, else `var(--color-ink-mute)`; it is `aria-hidden` with the list name following as `sr-only`. Accessible names the E2E spec depends on: `Options for <title>` on the menu trigger (same pattern as the sidebar row), `Plan <title>` on the Plan trigger. The menu trigger is hover/focus-revealed (`opacity-0` until `group-hover`/`focus-visible`/menu-open) and permanently visible on a coarse pointer (`[@media(pointer:coarse)]:opacity-100`), so touch users can reach the menu without hovering. On a coarse pointer the checkbox and both icon controls grow to 44px. The menu's first item is `Edit task…` (opens the editor; the same target as `Enter` on the row), then the `Move to list…` submenu (a disabled item when no other writable list exists), a separator, `Drop` and the danger-styled `Delete` (`DELETE /api/tasks/{id}`).

**Depends on / Used by** — `components/ui/checkbox`, `components/ui/dropdown-menu` (sub + item primitives), `components/ui/icons` (`MoreVerticalIcon`), `lib/color/palette` (`isHueFamily`, `shadeTokens`), `lib/domain/tasks` (`isOverdue`), `lib/time/format` (`formatWallDate`), `lib/services/tasks` (`TaskView`), `lib/ui/taskDrag` (`setTaskDragPayload`), `lib/utils` (`cn`), `./TaskPlanPopover`. Rendered by `TasksShell` inside `<ul aria-label="<View> tasks">`.

**Debugging** —

### components/tasks/TaskEditorDialog.tsx

**Purpose** — The task editor: one dialog for title, notes, due date and checklist, with Save and Delete. Opened by `TasksShell` on `Enter`, the row's "Edit task…" action and Task 11's `?task=` deep link; it only renders while a task is supplied.

**Public API** — `export function TaskEditorDialog(props: { task: TaskView | null; today: string; onClose: () => void; onDelete: (task: TaskView) => void })`. `today` is the household-local date for the due-date picker (a deviation from the plan's `{ task, onClose }` interface, needed for a correct Today button); `onDelete` exists because the shell owns the delete mutation and its undo toast. The body (`TaskEditorBody`, not exported) is keyed by `task.id`, so every open starts from the server snapshot.

**State & side effects** — Draft state: `title`, `notes` (plain text), `dueOn: string | null`, a checklist array of `{ key, title, done }` (server item ids as keys), the add-item field, the due-popover open flag and `useUpdateTask().isPending`. Save (form submit, or Enter in the title field) PATCHes one payload: `title` (trimmed; empty disables Save and shows the `role="alert"` "Give the task a title." under the field), `notes` (blank clears to `null`), `dueOn` and the **whole** `checklist` array as `{ title, done }` — Task 5's replace contract, so a save regenerates every item id. A save may move the task out of the open bucket (a due date); `onClose` runs after the PATCH and the shell's selection coherence handles the vanished row. A server 400/403 surfaces as an error toast (the shared `useUpdateTask` throws the envelope message) and the dialog stays open. Checklist controls: each item renders a `Checkbox` whose accessible name is the item title and a `Remove <title>` button; the add field (`New checklist item`, `#task-editor-new-item`) adds on Enter without submitting the form, and the `Add item` button is disabled while blank. The due field is a labelled (`Due date`) outline button showing `formatWallDate(dueOn)` or "No due date" that opens the shared `DatePickerPopover` in a non-modal popover, with a `Clear due date` action; Escape inside it closes only the calendar because the popover's Radix `DismissableLayer` is the highest layer while it is open — Radix's document-capture Escape handler dismisses that layer and the dialog's layer never sees the key (the file deliberately has no `stopPropagation`; a bubble handler would be a no-op against a capture listener). `Delete task` closes the dialog and calls `onDelete(task)`. Escape, `Cancel` and a successful save call `onClose`; `TasksShell` then restores focus to the selected row. Coarse-pointer targets are 44px; the scroll area pads 4px horizontally so focus rings are not clipped.

**Depends on / Used by** — `@radix-ui/react-popover`, `components/calendar/DatePickerPopover` (which renders `MiniMonth`), `components/ui/{button,checkbox,dialog,icons}`, `lib/query/tasks` (`useUpdateTask`), `lib/services/tasks` (`TaskView`), `lib/time/format` (`formatWallDate`), `lib/utils` (`cn`), `lib/validation/tasks` (`UpdateTaskInput`), `sonner`. Rendered by `components/tasks/TasksShell.tsx` (only mount).

**Debugging**
- The dialog opens with the previous task's text -> the body lost `key={task.id}` -> this file's `TaskEditorDialog`.
- Save does nothing -> the title is blank after trimming (Save disabled and the field shows its alert) or a PATCH is already in flight -> this file's `save`.
- Escape closes the whole editor while the due-date calendar is open -> the popover is not the topmost Radix layer (it must be portalled inside its own `PopoverPrimitive.Root` and actually open), so the dialog's `DismissableLayer` took the key; there is no `stopPropagation` to look for -> this file's `PopoverPrimitive.Root`/`Content`.
- Checklist edits look saved but revert after reload -> the PATCH sent a partial array or the service treated it as a diff; it must be the complete `checklist` -> `lib/services/tasks.ts` `replaceChecklist`.
- The new title/notes are gone after Escape -> intended: Escape and Cancel discard the draft (no dirty-guard confirm in this dialog) -> this file's `onClose`.
- Delete leaves the list unchanged -> the DELETE failed (view-only/partner list) -> read the toast from `TasksShell`'s `deleteTaskWithUndo`.

**Tests** — `tests/e2e/tasks.spec.ts` (the editor-persistence test): open a row with `Enter` (and once through the row menu's `Edit task…`), edit title + notes, add two checklist items, tick one, save, reload and assert the row/API payload, set a due date through the date popover (the task re-buckets Inbox → Today and paints the badge), clear it again (back to Inbox, badge gone, `dueOn: null`), then open again and assert Escape closes without saving. No component unit test (the repo has no React renderer); the PATCH/cache behaviour is covered by `tests/unit/task-cache.test.ts` and `tests/integration/tasks-api.test.ts`.
