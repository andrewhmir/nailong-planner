# v0.2.0 — Tasks & triage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.2.0 "Tasks & triage": every calendar becomes a *collection* that is a calendar or a list, lists and calendars share one private/shared/filtered tree, and a keyboard-first `/tasks` workspace captures, triages, schedules and completes tasks — with `private` collections unreachable by the partner at the API.

**Architecture:** One migration renames `calendar` → `collection` in place (adds `kind`, `visibility`, drops `is_view_only_for_partner`) and adds `task`/`task_checklist_item`. A single visibility resolver in `lib/services/collections.ts` gates every read and write path (tree, events, get-by-id, search, import). Buckets stay derived pure functions over date-only strings. The UI adds a mixed sidebar tree, a `/tasks` workspace in `components/tasks/`, and task chips on the FullCalendar month grid.

**Tech Stack:** Next.js 16 App Router · React 19 · TypeScript strict · Drizzle ORM + better-sqlite3 on SQLite · TanStack Query 5 · zod 4 · Tailwind v4 · FullCalendar 7 · Vitest 5 · Playwright 1.64.

**Spec:** `docs/superpowers/specs/2026-10-21-tasks-v0.2-design.md` (read §2 data model, §3 access control, §4 API, §5 UI, §8 test plan, §9 acceptance criteria). Loose pre-plan: `docs/superpowers/plans/2026-10-22-tasks-v0.2-loose.md`.

## Decisions settled (the loose plan's open questions)

- **D1 — Inbox:** one auto-created **private** `Inbox` list per user (`kind='list'`, `ownerId=user`, `visibility='private'`), created lazily by `ensureInbox(db, ctx)`; there is no shared inbox. Shared capture targets are ordinary shared lists.
- **D2 — Migration style:** in-place `ALTER TABLE calendar RENAME TO collection` (preserves rows) rather than copy-and-drop; hand-authored `0005` SQL plus a generated snapshot (recipe in Task 1).
- **D3 — Checklist API:** PATCH replaces the whole checklist (`checklist: {title, done}[]`); item ids are server-generated and not client-stable.
- **D4 — Privacy means invisible everywhere,** including search, counts, calendar chips and the derived views. The privacy integration test covers search too.
- **D5 — Drag:** native HTML5 drag (`draggable` task row → `dataTransfer` payload → `dayCellDidMount` listeners on the month grid), day-drop only. No FullCalendar Draggable integration, no time-slot blocks (v0.3).
- **D6 — Bucket predicates close a spec hole.** A task in a normal list with a `dueOn` but no `scheduledOn` must appear somewhere. Settled predicates (status `open`):
  - `inbox`: `collectionId = inbox` AND `scheduledOn IS NULL` AND `dueOn IS NULL`
  - `today`: `scheduledOn <= today` OR (`scheduledOn IS NULL` AND `dueOn <= today`)
  - `week`: (`scheduledOn > today` AND `scheduledOn <= endOfWeek`) OR (`scheduledOn IS NULL` AND `dueOn > today` AND `dueOn <= endOfWeek`)
  - `someday`: `scheduledOn IS NULL` AND `dueOn IS NULL` AND `collectionId != inbox`
  - `overdue`: `dueOn < today` — a cross-cutting badge/count on every view, not a view.
  `endOfWeek` respects `household.weekStartsOn` (0 = Sunday, 1 = Monday).
- **D7 — Kind is immutable** after creation; a child inherits its parent's kind. Owner and visibility are root-level: changing them on a root cascades to its children (same rule migration `0004` established for owners); editing them on a child is rejected `400`.
- **D8 — `kind` naming:** `collection = calendar | list`. Event UI keeps the `Calendar*` names (`components/calendar/`, calendar view); the data/services/API/query/sidebar layers use `Collection*`. The event calendar picker (`lib/ui/calendarPicker.ts`) keeps its name because it picks *calendars* (collection `kind='calendar'`).
- **D9 — Undo:** task complete/drop/delete/plan reuse the session stack: `pushUndo()` after success + `undoToast()`; delete-undo re-creates the task through `POST /api/tasks` with the captured payload (new id). No trash table in v0.2.

## Out of scope (the fence)

Recurring tasks, nested checklists, notes/focus/Today pages, notifications, command palette, kanban, time-slot blocks (`event.taskId`), ICS export/subscriptions/reminders, and the calendar-spec Track B switch kit (those are v0.3+; see `docs/superpowers/specs/2026-10-21-calendar-ux-parity-design.md` §8.2 for the separate track).

## Review Focus

The failure modes most likely to bite a household user, each pinned to a test in the task that owns the code:

1. **A task in a private list leaks to the partner through an unfiltered read** (search, counts, event chips, get-by-id). *Pinned in Tasks 3 and 12 (integration privacy matrix + search; E2E scenario 5).*
2. **A due-only task in a project list is invisible in every view** (the spec's bucket table has this hole). *Pinned in Task 4 (due-fallback buckets; unit tests for both week starts).*
3. **A day shifts because the client formats a date with `toISOString()`** (Taipei UTC+8: 00:30 local becomes yesterday UTC). *Pinned in Tasks 4/8 (date-only helpers; E2E reload persistence in Task 12).*
4. **Migration replay on a real v0.1 database loses an event, parent link, colour or the view-only flag.** *Pinned in Task 1 (pre-0005 fixture: 0000–0004 applied, data inserted, then 0005; asserts every column survives and `visibility` backfills).*
5. **A failed task mutation or undo leaves stale optimistic rows/counts.** *Pinned in Task 10 (cache rollback + undo restores exactly once; integration rejects a cross-list reorder in Task 5).*
