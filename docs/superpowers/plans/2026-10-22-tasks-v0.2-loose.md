**Goal:** make Nailong Planner the place tasks are managed — capture, triage,
schedule, complete — with three-state privacy that is enforced server-side.

**Non-goals:** recurring tasks, sub-tasks beyond a flat checklist, notes, focus,
the composed Today page, notifications, a command palette, any kanban view, and
time-slot blocking (that is v0.3).

**Prerequisite:** `main` clean. The rail shipped in v0.1.0 (`5cd022b`); any
in-flight calendar fix lands first so the migration is not rebased over uncommitted
edits.

---

## Phases

Six phases, one commit-worthy slice each. Phases 1–2 are the risky half and carry
the whole migration; 3–5 are UI and can be reordered.

### Phase 1 — Collection and task schema

- Generalise `calendar` → `collection` with `kind: calendar | list` and
  `visibility: shared | view_only | private`; replace `isViewOnlyForPartner`.
- Migration `0004`: copy rows (`kind='calendar'`), backfill visibility, rename the
  events FK, drop the old flag.
- New tables: `task`, `task_checklist_item`.
- Migration test: pre-v0.2 data keeps every event, parent link and colour.
- Mechanical rename across services/queries/handlers/import **before** any UI work;
  the suite must be green at the end of this phase.

### Phase 2 — Domain rules and API

- `resolveVisibleCollections(userId)` / `assertWritable(collection, userId)`;
  every task query joins through the resolver.
- Derived buckets (`inbox`, `today`, `week`, `someday`, `overdue`) as pure
  functions with day/week-boundary unit tests.
- Validation: a private collection requires an owner; inbox is auto-created per
  household and private to its creator.
- Handlers/routes: `/api/collections`, `/api/collections/[id]`, `/api/tasks`,
  `/api/tasks/[id]`, `/api/tasks/order`.
- Privacy integration test: partner gets 404 (not 403) for a private collection by
  id, and list/get/patch/delete all fail.

### Phase 3 — Mixed sidebar tree

- Lists and calendars in one tree, shade inheritance unchanged, `New list` /
  `New calendar` in one menu.
- Visibility control on the row menu with a lock for private collections; the
  partner never receives the row.
- Extend `useVisibility` / `useTreeFold` for collection ids and `kind`; audit the
  sidebar for "every node is a calendar" assumptions.

### Phase 4 — Task workspace

- `/tasks` route, crumb, rail entry flipped `live` in `lib/roadmap.ts` by the
  release commit.
- Capture bar (`Enter` → Inbox, `Shift+Enter` → Today), view switcher with counts,
  task rows with due badge and collection dot.
- Triage keys: `j`/`k`, `1` Today, `2` This week, `3` Someday, `4` next list,
  `x` complete; global `Shift+K` capture.
- Plan action (date picker → `scheduledOn`).

### Phase 5 — Calendar integration

- Month grid: one chip per scheduled task on its day, "+N more" expansion, click
  opens the task.
- Drag a task row onto a month day → sets `scheduledOn` (no block).
- Day-drop only; no cross-view drag plumbing.

### Phase 6 — Docs, seed, release

- Component docs, `DEBUGGING.md` traps, `tests.md` rows, README, CHANGELOG.
- Seed one list per user, a shared `Ours` list, tasks in every bucket, for E2E and
  screenshots.
- Fresh screenshots; `package.json` → `0.2.0` **and** `APP_VERSION` in
  `lib/roadmap.ts` in the same commit; roadmap entry for Tasks goes `planned` →
  `live`.

## Open decisions (settle before Phase 1)

1. **Inbox scope.** One auto-created Inbox per user, or a shared Inbox as well?
   Spec says per-creator private; confirm a shared capture target is not wanted.
2. **Migration style.** Rename `calendar` in place (fewer rows, wider diff) vs
   create `collection` and copy (reversible, one extra table during migration).
3. **Checklist API shape.** Replace the whole checklist on task PATCH (simplest,
   matches event payload style) vs granular item endpoints.
4. **Private means invisible everywhere** — including search and the derived
   totals; confirm search is in scope for the privacy test.
5. **Drag implementation.** Native HTML5 drag from the task list onto the month
   grid, or reuse the calendar's existing pointer-drag machinery.

## Risks

- **Migration churn** breaks import and search, which touch calendars heavily →
  phase 1 is a standalone green commit, no UI mixed in.
- **Tree assumptions**: sidebar code assumes every node is a calendar → unit-test
  the hooks with lists; E2E the sidebar again.
- **Privacy leak** through a query that bypasses the resolver → one resolver,
  no ad-hoc filtering, and the 404 test.
- **Scope creep** into blocks/Today/notes → the non-goals above are the fence.

## Done when

All six spec acceptance criteria hold: keyboard-only capture→triage→schedule→
complete; ten-task inbox triaged under a minute; a private collection unreachable
for the partner at the API; calendar behaviour unchanged; `docs:check`, `lint`,
`typecheck`, `test` and the owning Playwright specs green; no version literal
outside `lib/roadmap.ts`.
