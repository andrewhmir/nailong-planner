# v0.2.0 — Tasks & triage — design

- **Status:** Draft for review
- **Date:** 2026-10-21
- **Parent:** `docs/superpowers/specs/2026-10-21-productivity-roadmap-design.md`
- **Depends on:** nothing unshipped. First pillar after the shipped calendar.

## 1. Goal

Make Nailong Planner the place tasks are managed: capture in a keystroke, triage a
small inbox to zero, schedule work onto a day, move it onto the calendar grid, and
complete it — with per-collection privacy that is real, not cosmetic.

**Non-goals for v0.2:** recurring tasks, sub-tasks (a task has a flat checklist),
notes, focus/timer, Today's composed page, notifications, a command palette, and any
kanban view. "Today" exists in v0.2 only as a *smart view inside the Tasks page*;
the composed Today home is v0.3.

## 2. Data model

### 2.1 `collection` (migrated from `calendar`)

`lib/db/schema.ts` currently defines `calendar` with exactly the tree and ownership
fields this needs — `parentId`, `hueFamily`, `shadeIndex`, `sortOrder`, nullable
`ownerId` (null = ours), `isViewOnlyForPartner`. Generalise it in place:

| Column | Change |
|---|---|
| `kind` | **new** — `calendar` \| `list`. Existing rows `calendar`. |
| `visibility` | **new** — `shared` \| `view_only` \| `private`. |
| `isViewOnlyForPartner` | **replaced** by `visibility` (`1` → `view_only`, `0` → `shared`). |
| `ownerId` | unchanged; nullable owner means "Ours". |
| tree/colour/order columns | unchanged. |

Table renamed `calendar` → `collection`; indexes keep their names where Drizzle
allows, otherwise renamed in the same migration. Backfill runs in the migration:
every existing row gets `kind='calendar'` and the `visibility` value derived from
`isViewOnlyForPartner`.

**Visibility semantics**

| Value | Partner can read | Partner can write | Notes |
|---|---|---|---|
| `shared` | yes | yes | the current default; "Ours" |
| `view_only` | yes | no | today's view-only calendar, generalised |
| `private` | **no** | no | filtered server-side; never serialised |

`private` requires `ownerId != null`. A collection whose `ownerId` is null cannot be
private — enforced by validation, not just convention.

### 2.2 `task`

| Column | Type | Notes |
|---|---|---|
| `id` | text pk | |
| `householdId` | fk household | cascade |
| `collectionId` | fk collection | cascade; the list the task belongs to |
| `title` | text not null | |
| `notes` | text nullable | plain text/markdown-lite, rendered the same way event notes are |
| `status` | `open` \| `done` \| `dropped` | default `open` |
| `scheduledOn` | date text nullable | "I'll work on this day" — drives Today and the Week view |
| `dueOn` | date text nullable | deadline; drives the overdue badge |
| `completedAt` / `droppedAt` | integer nullable | audit |
| `sortOrder` | integer not null default 0 | manual order within a collection and bucket |
| `createdBy` | text not null | who captured it |
| `createdAt` / `updatedAt` | integer | |

Dates are **date-only strings** (`YYYY-MM-DD`), not epochs: a task is a calendar-day
commitment, not an instant. This is deliberately unlike `event.startAt` (epoch ms).

**Buckets are derived, never stored.** Storing a bucket makes it stale at midnight.

| View | Predicate (status = open) |
|---|---|
| Inbox | `scheduledOn IS NULL AND dueOn IS NULL AND collectionId` is the inbox list |
| Today | `scheduledOn <= today` |
| This week | `scheduledOn > today AND scheduledOn <= endOfWeek` |
| Someday | neither `scheduledOn` nor `dueOn` set, outside the inbox |
| Overdue | `dueOn < today` (cross-cutting badge on any view) |

The **Inbox is a real collection** (auto-created per household, named `Inbox`, kind
`list`, private to its creator by default) rather than a magic predicate, so tasks
cannot be stranded without somewhere to live. The Inbox bucket additionally excludes
tasks that already have a date.

### 2.3 `task_checklist_item`

`id`, `taskId` (cascade), `title`, `done` (0/1), `sortOrder`. Flat; no nesting.

### 2.4 Time blocks are deferred to v0.3

v0.2 does **not** add `taskId` to events and does not create time blocks: a task
carries a day (`scheduledOn`), and the month grid renders scheduled tasks as small
chips on that day. v0.3 adds `event.taskId` and drag-to-time-slot, at which point a
block is an ordinary event and needs no new table. Deferred so the v0.2 migration
stays small and day-level planning ships first.

### 2.5 Ordering

Integer `sortOrder`, renumbered within a list on drag (small lists, two users; a
lexorank scheme is not worth the complexity yet). The renumber write is one PATCH
to `/api/tasks/order` carrying the ordered ids.

## 3. Access control

One resolver, `lib/services/collections.ts` (extending `lib/services/calendars.ts`
and `lib/services/permissions.ts`):

- `resolveVisibleCollections(userId)` — returns shared, view-only and the user's own;
  excludes every `private` collection not owned by `userId`.
- `assertWritable(collection, userId)` — rejects `view_only` for non-owners, rejects
  `private` for non-owners, rejects everything if the household does not match.
- Every task query joins through the resolver. A task is never fetched by id without
  the resolver's collection in scope.

**Test invariant:** a private collection and its tasks must be
unreachable from the partner's session at the API layer (404, not 403 on read-by-id,
so existence is not leaked).

## 4. API

Follow the existing shape: `app/api/<resource>/route.ts` → `lib/api/handlers/*` →
`lib/services/*` → `lib/query/*`, with `lib/validation/*` schemas.

| Route | Methods | Notes |
|---|---|---|
| `/api/collections` | GET, POST | GET returns the unified tree (calendars + lists) with `kind`, `visibility` |
| `/api/collections/[id]` | PATCH, DELETE | PATCH covers rename, hue, visibility, re-parent, sort order |
| `/api/tasks` | GET, POST | GET takes `view=inbox\|today\|week\|someday\|overdue`, `collectionId` |
| `/api/tasks/[id]` | PATCH, DELETE | PATCH covers title, notes, dates, status, checklist replace |
| `/api/tasks/order` | PATCH | ordered ids for one list |

`POST /api/tasks` returns the created task so quick capture can clear its input
optimistically; failures toast the same way event creation does today.

## 5. UI

### 5.1 Rail and routes

- New rail entry `Tasks` → `/tasks` (roadmap status `live` in v0.2.0). Calendar,
  Today, Notes, Focus gated per the roadmap; Tasks becomes the first item flipped
  live in this version.
- `/tasks` renders `TasksPage`: left side is the existing shell sidebar with the
  unified tree (mini-month stays, optional for Tasks); main area is the task workspace.

### 5.2 Task workspace

- **Capture bar** pinned at the top: one input, `Enter` saves to the Inbox,
  `Shift+Enter` saves to Today. Placeholder: "Add a task…".
- **View switcher** (segmented, like the calendar's): Inbox · Today · Week · Someday.
  Counts as badges; overdue count on the collection rows.
- **Task row**: checkbox, title, due badge, collection dot, "Plan" and overflow
  (move to list, drop, delete).
- **Triage flow** — the point of the feature: `j`/`k` move, `1` Today, `2` This week,
  `3` Someday, `4` next list, `Enter` opens the row, `x` completes. A shortcut sheet
  exists already; extend it.
- **Quick capture globally:** `Shift+K` opens the capture bar from anywhere in the
  app (check for collision with existing `Shift+C`; `Shift+K` is free and mirrors
  Linear/Things). Single-key shortcuts must keep their "never while typing" rule.

### 5.3 Tree changes

`components/sidebar/CalendarTree.tsx` becomes a mixed tree:

- One "New" menu: **New list** and **New calendar**.
- Each row shows a list icon vs calendar swatch; the shade-inheritance rules apply
  to lists too, so `Work > Client A` reads as one family.
- Visibility affordance on hover/open menu: `Shared` / `View only` / `Private`
  (private rows show a lock; the partner never sees the row at all).
- Fold state and per-calendar visibility toggles reuse `lib/ui/useTreeFold.ts` and
  `lib/ui/useVisibility.ts`; the latter learns collection ids and `kind`.
- Only events filter against calendar visibility; the tree must not assume every
  node is a calendar (search `components/sidebar` for `.calendar` assumptions).

### 5.4 Calendar integration

- Calendar month view: one small chip per scheduled task on its day — list colour
  and completion state, capped and expanded with the grid's existing "+N more"
  affordance. Clicking a chip opens the task, not event details.
- "Plan" on a task sets `scheduledOn` via the date picker (reuse
  `components/calendar/` picker).
- **Drag**: v0.2 ships task-row drag onto a month-grid day (sets `scheduledOn`).
  Drag onto a *time slot* to create a linked event block is a v0.3 item, so v0.2
  does not need cross-view drag plumbing.

## 6. Migration and compatibility

1. `0004_collections_and_tasks.sql`: create the new tables/columns, copy calendar
   rows into `collection` (`kind='calendar'`), backfill `visibility`, move events'
   FK to `collectionId` (column stays `calendar_id` → renamed to `collection_id` in
   the same migration), drop `is_view_only_for_partner`.
2. Follow the existing drizzle pattern (`drizzle/*.sql` + `drizzle/meta`) and
   `lib/db/migrate.ts`; `tests/integration/db.test.ts` gains migration assertions.
3. `lib/import/ics.ts` and the import handler target `collection` with
   `kind='calendar'`; import never creates lists or private collections.
4. The seed script `scripts/seed-test-db.mts` gains one list per user, a shared
   `Ours` list, and a few tasks in each bucket so E2E and screenshots are meaningful.

## 8. Test plan

**Unit**
- bucket derivation: day boundaries, week edges (respecting week-start preference),
  overdue vs Today, inbox exclusion.
- visibility resolver: every combination of owner/requester/visibility.
- validation: private collection without an owner is rejected.

**Integration**
- private list + tasks invisible to partner: list, get-by-id, patch, delete all fail.
- view-only: partner can read, cannot write.
- migration: pre-v0.2 data preserves every event, parent link and colour.
- ordering endpoint rejects a partial or cross-list id set.

**E2E** (`tests/e2e/tasks.spec.ts`, new)
1. Create a list, capture three tasks, triage one to Today, one to Week, one left in
   Inbox; reload; state persists.
2. `Shift+K` from the calendar creates an Inbox task without navigating.
3. Plan a task for a date; it appears in Today/Week correctly and in the month grid.
4. Complete a task; it leaves the open view; undo restores it.
5. Sign in as the other user: private list and its tasks do not exist.

## 9. Acceptance criteria

1. Capture → triage → schedule → complete works with the keyboard alone.
2. Inbox triaged to zero in under a minute for ten tasks.
3. A `private` collection is unreachable for the partner at the API, not just
   visually hidden.
4. The tree shows calendars and lists together; existing calendar behaviour
   (shade inheritance, fold state, visibility toggle, view-only) is unchanged.
5. `npm run docs:check`, `lint`, `typecheck`, `test` pass; the owning Playwright
   specs pass; no full-suite run as an edit loop.
6. No version literal outside `lib/roadmap.ts`.

## 10. Risks

| Risk | Mitigation |
|---|---|
| Rename churn across every calendar query | Mechanical, one migration, do it before any UI work; suite must be green before the tree changes |
| Mixed tree breaks calendar-only assumptions in sidebar code | Unit-test `useVisibility`/`useTreeFold` with lists; E2E covers sidebar behaviour |
| User-defined date semantics (scheduled vs due) confusing | Two distinct badges, distinct labels, and the triage shortcuts never set `dueOn` |
| Drag scope creep into v0.3 time-slot blocking | Written as a non-goal; v0.2 drag is day-drop only |
