# Nailong Planner — v0.1.0 Design Spec

- **Date:** 2026-10-19
- **Status:** Draft for review
- **Authors:** Andrew + planning session (Lead)
- **Visual reference:** `.superpowers/mockups/option-2-cozy.html` (chosen direction: "Cozy companion"; mockups are throwaway artifacts, not production code)

---

## 1. Summary

Nailong Planner is a small, private, web-based planner for exactly two people. v0.1.0 is a calendar that borrows Google Calendar's interaction model — multiple color-coded calendars, per-calendar visibility toggles, click-to-create events — and adds one idea Google Calendar does not have: **a two-level calendar hierarchy where sub-calendars are rendered in shades of their parent's color**, so a whole area of life (School) reads as one visual family while its parts (Math, Biology) stay distinguishable.

The two users share one **household**. Everything is visible to both. A per-calendar **"view only" flag** lets one partner look at, but not modify, a calendar the other owns. A **person cross-check toggle** in the top bar shows or hides all of the other person's calendars in one click.

The app is hosted publicly and therefore requires authentication; there is no public sign-up and exactly two accounts exist.

**Success looks like:** both people open it daily without thinking about it, the month view is readable at a glance, and neither person ever has to reconcile two different calendars manually.

## 2. Goals and non-goals

### Goals (v0.1.0)

1. Create, rename, recolor, reorder and delete top-level calendars and two-level sub-calendars.
2. Sub-calendars automatically receive distinct shades of the parent's hue family and re-shade when the parent's hue changes.
3. Create, edit, move, resize and delete events in month, week, day and list views.
4. Recurring events (RFC 5545 RRULE) createable and editable as a series; a single occurrence can be skipped.
5. All-day and timed events, stored so that neither drifts across timezones.
6. Per-calendar visibility toggles plus one-click person-level cross-check.
7. Per-calendar "view only" enforcement on the server, not just in the UI.
8. Secure login for exactly two accounts, with TOTP two-factor authentication available and recommended.
9. Deployable as one Docker container to Railway today, and portable to another host later.

### Non-goals (v0.1.0)

- No reminders, notifications, email, or push.
- No Google Calendar sync, ICS import/export, or CalDAV.
- No per-occurrence overrides (only "skip this occurrence").
- No dark mode, no PWA install, no offline mode.
- No tasks, notes, lists, meals, budgets, chores, or attachments.
- No multi-household, no third (or more) user, no sharing links.
- No public sign-up, no email delivery, no password-reset-by-email flow.
- No realtime collaboration; concurrent edits resolve last-write-wins.

## 3. Users, roles and permissions

### Identities

- **Household** — the single tenancy row. Every query is scoped by `household_id`.
- **Member** — a user belonging to the household. There are exactly two in practice; the schema allows more but provisioning blocks more than two.
- **Calendar owner** — a calendar may be owned by user A, user B, or nobody (a shared "Ours" calendar).

### Rules

| Action | Rule |
|---|---|
| Read any calendar / event in the household | Any member. Everything is visible to both members. |
| Create a top-level calendar | Any member. Chooses owner: me / partner / ours. Only "ours" (owner = NULL) and own calendars can be created by that member. |
| Create a sub-calendar | Any member, under any top-level calendar they can write to. |
| Edit calendar metadata (name, hue, order, owner) | Any member, except on a calendar that is `is_view_only_for_partner` and owned by the other member. |
| Toggle `is_view_only_for_partner` | **Only the calendar's owner.** A calendar with owner NULL ("ours") cannot be made view-only. |
| Delete a calendar | Any member with write access. Deleting a top-level calendar deletes its sub-calendars and their events (confirmation required in UI). |
| Create / edit / move / delete an event | Any member who can write to the event's calendar. |
| Access any page or API route | Authenticated member of the household. |

The write predicate lives in exactly one function (`canWriteCalendar(userId, calendar)`) used by every mutation. It is enforced server-side; the UI only hides affordances.

## 4. Domain model

SQLite, accessed through Drizzle ORM. Authentication tables are generated by Better Auth and are not hand-authored (see §9). Domain tables:

### `household`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | nanoid |
| `name` | text | display name, default `Our Nest` |
| `timezone` | text | IANA zone, default `Asia/Taipei` |
| `week_starts_on` | integer | 0 = Sunday (Google's Taiwan default) |
| `created_at` | integer | epoch ms |

Exactly one row in v0.1.0.

### `member`

| Column | Type | Notes |
|---|---|---|
| `user_id` | text PK | references Better Auth `user.id`, cascade delete |
| `household_id` | text | references `household.id` |
| `role` | text | `owner` / `member`; both members are `owner` in practice |
| `created_at` | integer | epoch ms |

### `calendar`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | nanoid |
| `household_id` | text | scoping column, indexed |
| `parent_id` | text NULL | self-reference; `ON DELETE CASCADE`. NULL = top-level. |
| `name` | text | 1–60 chars |
| `hue_family` | text NULL | key into the palette (see §5). **Required on roots, NULL on children.** |
| `shade_index` | integer | 0–7; meaningful only on children. Roots render at `PARENT_SHADE_INDEX`. |
| `owner_id` | text NULL | user id, or NULL for "Ours" |
| `is_view_only_for_partner` | integer (bool) | default 0 |
| `sort_order` | integer | display order within siblings |
| `created_at`, `updated_at` | integer | epoch ms |

**Two-level invariant:** a calendar with a non-NULL `parent_id` must point at a calendar whose own `parent_id` IS NULL, and both must share the same `household_id`. Enforced in the service layer and covered by an integration test.

**Cascade:** deleting a root deletes children; deleting any calendar deletes its events.

### `event`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | nanoid |
| `household_id` | text | scoping column, indexed |
| `calendar_id` | text | references `calendar.id`, `ON DELETE CASCADE` |
| `title` | text | 1–200 chars |
| `description` | text NULL | ≤ 4000 chars |
| `location` | text NULL | ≤ 200 chars |
| `all_day` | integer (bool) | |
| `start_at`, `end_at` | integer NULL | **epoch ms UTC**, used when `all_day = 0` |
| `start_date`, `end_date` | text NULL | `YYYY-MM-DD`, **household-local**, used when `all_day = 1`; `end_date` inclusive |
| `rrule` | text NULL | RFC 5545 RRULE string, e.g. `FREQ=WEEKLY;BYDAY=TU` |
| `exdates` | text NULL | JSON array of ISO datetimes that were skipped |
| `created_by` | text | user id |
| `created_at`, `updated_at` | integer | epoch ms |

**Storage invariant:** `all_day = 1` ⇒ `start_date`/`end_date` set and `start_at`/`end_at` NULL; `all_day = 0` ⇒ the reverse. Timed events are stored as UTC instants; all-day events are stored as local calendar dates so they can never shift a day when the server timezone changes.

`exdates` entries use the event's own domain — `YYYY-MM-DD` for all-day events, ISO 8601 UTC instants for timed events. `end_date` is **inclusive** in the database; the FullCalendar adapter converts to its exclusive-end convention at exactly one boundary (unit-tested).

**Indexes:** `calendar(household_id)`, `calendar(parent_id)`, `event(household_id, start_at)`, `event(calendar_id)`, `event(household_id, start_date)`, `event(household_id, rrule)`.

## 5. Color system and hierarchy rules

### Hue families (10)

`teal, green, lime, amber, orange, rose, violet, indigo, sky, slate` — each defined in OKLCH as a hue + chroma pair, so all shades within a family keep a constant perceptual hue.

### Shades (8)

Each family exposes 8 lightness steps (`shade_index` 0–7, light → dark) computed from the family's OKLCH hue/chroma with a fixed lightness ramp. Derived tokens per (family, shade):

- `main` — the saturated color used for dots, borders and drag highlights
- `container` — a soft paper-tinted fill for event blocks
- `onContainer` — text color on `container` (dark ink for steps 0–3, near-white for steps 4–7)

### Assignment rules

1. A **root** calendar stores `hue_family` and renders at the fixed `PARENT_SHADE_INDEX` (3).
2. A **child** calendar inherits its parent's `hue_family` and is assigned the next unused `shade_index` from the sequence `[4, 2, 5, 1, 6, 0, 7]`. Maximum **7 sub-calendars per root**; the API rejects an eighth with a friendly error.
3. Changing a root's `hue_family` re-derives every child's rendered color automatically — no per-child writes.
4. Deleting a child frees its shade for the next created child.
5. Children never store a hex color, so they can never drift off-hue.

Palette computation lives in one shared module (`lib/color/palette.ts`) imported by both server and client; it is pure and unit-tested (8 distinct steps per family; contrast token correct per step).

## 6. UX specification

### Visual direction

"Cozy companion": warm paper background, soft rounded surfaces, terracotta accent, a small dragon mascot in the header, generous radii (18–26 px), 1 px warm borders, soft shadows.

Core tokens:

| Token | Value |
|---|---|
| `--paper` | `#f6efe6` |
| `--surface` | `#fffdfa` |
| `--card` | `#ffffff` |
| `--line` | `#efe3d3` |
| `--line-strong` | `#e6d7c4` |
| `--ink` | `#4a3f36` |
| `--ink-soft` | `#7b6a5c` |
| `--ink-mute` | `#a8988a` |
| `--accent` | `#e07a5f` |
| `--accent-soft` | `#fbe3d6` |
| `--accent-ink` | `#b55a3d` |

Typography: system UI stack; 12.5–14 px base, weights 600/700 for headings and labels. Month-cell detail is dot-based so it stays legible at phone width.

### Layout

**Desktop (≥ 1024 px):** fixed left sidebar (280 px) with the calendar tree; top bar spanning the content area (brand, month label, ‹ Today ›, view switcher, person pills, "+ Event"); calendar grid fills the remainder.

**Tablet (768–1023 px):** sidebar collapses to an icon rail; tree opens as an overlay panel.

**Mobile (< 768 px):** single column; top bar compresses (brand mark + month label + add button); tree opens as a bottom sheet; default view is **list (agenda)** because month dots are cramped at 375 px.

### Calendar tree (sidebar)

- Group headers: `OURS`, `MINE · <name>`, `HERS · <name>` (labels derived from household members; "OURS" first).
- Root row: checkbox, color swatch, name, and a shade strip — the first three child shades, or the family ramp when it has no children yet.
- Child row: indented 22 px, checkbox, single swatch, name, optional `view only` pill.
- Root rows have a hover menu: *Add sub-calendar*, *Rename*, *Change color*, *Delete*.
- Child rows have a hover menu: *Rename*, *Delete*.
- Checkbox = per-calendar visibility. Group visibility multiplies with the checkbox (a calendar hidden by its group pill stays hidden even if checked).
- A root checkbox toggles the whole group (root + children) and renders indeterminate when mixed.
- Visibility state is a per-device UI preference stored in `localStorage`, keyed by user id.

### Person pills (top bar)

Three pills: `Ours`, `<me>`, `<partner>`. Each toggles the whole group's visibility; pills visibly dim when off. This is the "quick cross-check".

### Calendar grid

FullCalendar v7, custom toolbar (FullCalendar's own header is disabled), household timezone, Sunday week start.

- **Month:** colored dots per day (one per visible calendar with events that day, max 4 then "+N"); a readable day cell ≥ 36 px tall.
- **Week / day:** time-grid with rounded event blocks; overlapping events side-by-side; `now` indicator.
- **List:** agenda rows grouped by day.
- Click/drag an empty slot → quick-create dialog with the calendar pre-selected if only one is visible.
- Click an event → popover: title, time, calendar, description; buttons *Edit*, *Delete*.
- Drag an event → change its start; drag its edge → change duration. On drop, PATCH and show optimistic update.
- Recurring events show a subtle repeat glyph.

### Event dialog

Fields: title (required), calendar (select from visible/writable calendars), all-day toggle, start/end (date-time or date), description, location, repeat (none / daily / weekly / monthly / yearly, plus interval and weekday pickers for weekly).

Deleting a recurring event asks scope: **This event** (adds that occurrence to `exdates`) or **All events** (deletes the series).

Editing a recurring event always edits the series in v0.1.0. Per-occurrence overrides are out of scope, so the edit dialog offers no scope choice and states plainly that changing one occurrence means changing the series.

### Settings

Minimal page at `/settings`:
- Profile: display name, change password.
- Security: TOTP two-factor enrolment (QR + one-time backup codes), active sessions with revoke.
- Household: name, timezone, week start (members-only, both can edit).
- About: version.

### States

Empty (no calendars / no events / filtered everything out), loading skeletons for the grid, inline field errors in dialogs, toast for mutation success/failure, explicit "you have view-only access" notice when opening a read-only event.

### Accessibility

Dialogs and popovers are keyboard operable with visible focus rings; icons have accessible labels; dots are never the only carrier of information (day cell tooltip/agenda provides text); `prefers-reduced-motion` respected.

## 7. API

All routes are JSON, authenticated by session cookie, and scoped to the caller's household. Validation with Zod. Error shape:

```json
{ "error": { "code": "FORBIDDEN", "message": "This calendar is view-only.", "fields": { "name": "Required" } } }
```

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | liveness + DB check, unauthenticated |
| ALL | `/api/auth/*` | Better Auth handlers |
| GET | `/api/session` | current user, household, members; 401 when signed out |
| GET | `/api/calendars` | calendar tree (roots with nested children) |
| POST | `/api/calendars` | create root or child |
| PATCH | `/api/calendars/:id` | rename, recolor root, move owner (own calendars only), toggle view-only (owner only), reorder |
| DELETE | `/api/calendars/:id` | delete calendar (cascades) |
| GET | `/api/events?from=&to=` | events in range: non-recurring rows intersecting the range **plus** every recurring row (expanded client-side) |
| POST | `/api/events` | create event |
| PATCH | `/api/events/:id` | update event (always the whole series for recurring events) |
| DELETE | `/api/events/:id` | delete; body `{ scope: "all" \| "this", occurrenceStart?: string }` — `this` appends that occurrence to `exdates` |

Status codes: 200/201 success, 400 validation, 401 unauthenticated, 403 permission denied, 404 not found, 409 constraint conflict (e.g. eighth sub-calendar), 429 rate-limited, 500 unexpected.

The event payload sent to the client already includes resolved `color` / `contrastColor` for its calendar, so the calendar component never computes palette logic.

## 8. Architecture and stack

Single Next.js application, one process, one database file.

| Layer | Choice | Version policy |
|---|---|---|
| Framework | Next.js App Router, TypeScript, `output: "standalone"` | Next 16 (current stable); pin exact at scaffold. Fall back to 15.5.x only if a peer-dependency blocker appears. |
| UI runtime | React 19 | matches Next peer range |
| Calendar | **FullCalendar v7** (`@fullcalendar/react` 7.1.3) + `@fullcalendar/rrule` 7.1.3 + `rrule` 2.8.x + `temporal-polyfill` 1.0.x | **pin exact** (`7.1.3`, no caret): v7 is stable and maintained (v6 is `legacy`), has real React SSR/StrictMode support, no CSS injection, and IANA timezones built in via Temporal |
| Styling | Tailwind CSS 4 + shadcn/ui (Radix primitives) with the cozy token layer | pin exact |
| Data fetching | Drizzle ORM + better-sqlite3, WAL mode | pin exact |
| Client cache | TanStack Query | pin exact |
| Auth | Better Auth 1.7.x with Drizzle adapter + admin plugin + twoFactor plugin | pin exact |
| Validation | Zod | pin exact |
| Tests | Vitest (unit + integration), Playwright (E2E) | pin exact |

### Data flow

- Server Components render the app shell and load initial data directly through the data layer (no HTTP hop).
- Mutations go through route handlers (§7); handlers call service functions, which own validation, the two-level invariant, the permission predicate and every household-scoped query.
- The client holds calendars and events in TanStack Query, refetching the visible date range whenever the view or range changes. No websockets, no polling.

### Repository layout

```
app/                     # routes: (app) shell, login, api/*, settings
components/
  calendar/              # FullCalendar wrapper, toolbar, event dialog, popover
  sidebar/               # calendar tree, group headers, row menus
  ui/                    # shadcn primitives
lib/
  db/                    # drizzle schema, client, migrations runner
  auth/                  # better-auth config, provisioning, session helpers
  services/              # calendars, events, permissions
  color/                 # palette + shade assignment
  time/                  # date/tz helpers, all-day handling
  validation/            # zod schemas
scripts/                 # provision users, reset password, backup
tests/                   # vitest unit + integration, playwright e2e
docs/superpowers/        # this spec and the implementation plan
```

### Timezone rules

- Household timezone is the single rendering and expansion timezone.
- Timed events: store UTC epoch ms; render and expand in household timezone.
- All-day events: store local `YYYY-MM-DD`; never convert through UTC.
- FullCalendar is configured with `timeZone: household.timezone`.
- Recurrence expansion must preserve local wall-clock time across DST changes (a 09:00 weekly event stays 09:00 after a shift). Covered by a DST-crossing unit test.

## 9. Authentication and security

### Accounts

- Email + password via Better Auth, `emailAndPassword.disableSignUp: true`, `minPasswordLength: 12`.
- The two accounts are created by `scripts/provision.mjs` (idempotent; reads `SEED_USER_1_*` / `SEED_USER_2_*` env vars) using Better Auth's server API and the admin plugin. **There is no public setup route and no public sign-up.**
- A `databaseHooks.user.create.before` guard rejects any creation beyond two users, so a config regression cannot open registration.
- Password reset has no email flow: `scripts/reset-password.mjs` is the documented break-glass procedure.

### Sessions

- DB-backed, revocable; 7-day expiry, 1-day rolling update.
- Cookie: `httpOnly`, `Secure` (https base URL), `SameSite=Lax`.
- CSRF: Better Auth origin validation kept on, exact `trustedOrigins`, `disableOriginCheck` never set.

### Two-factor

- TOTP plugin enabled; enrolment at `/settings/security` with QR code and ten single-use backup codes shown once (and printable).
- Recommended for both accounts; the app surfaces a persistent banner until both members have enrolled.
- Challenge is issued in place of a session, so an unverified login is never authenticated.

### Rate limiting and proxy trust

- Better Auth rate limiting enabled with **database storage** (in-memory would be per-instance).
- Behind Railway's proxy, configure `advanced.ipAddress.ipAddressHeaders` to the header Railway sets (`x-forwarded-for`) — the container is not otherwise publicly reachable, so that header is trustworthy in this deployment.
- An additional brute-force throttle on the auth route: a database-backed counter of failed sign-ins per IP and per account (10 failures / 15 minutes), independent of Better Auth's built-in limiter.

### Application hardening

- Middleware protects every route except `/login`, `/api/auth/*`, `/api/health`, and static assets.
- Security headers: HSTS, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `Permissions-Policy` minimal, `X-Robots-Tag: noindex`, and a CSP started in report-only mode then tightened.
- Every query passes through the household-scoped data layer; no raw `db.select()` in route code.
- No secrets in the repo; `.env*` gitignored; `.env.example` documents every variable.

## 10. Deployment and operations

### v0.1.0 target: Railway (one container)

- Multi-stage `Dockerfile` (`node:22-bookworm-slim`, non-root user, Next standalone output), works on both amd64 and arm64.
- Railway config: Dockerfile build, health check `/api/health`, restart on failure, one volume mounted at `/data`, one instance only (SQLite ⇒ never scale horizontally).
- Entrypoint applies Drizzle migrations before starting the server (single instance ⇒ no migration race).
- Env vars: `DATABASE_URL=file:/data/planner.db`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `NODE_ENV=production`, `TZ=Asia/Taipei`.
- Expected cost at this scale: **~$5–6/month** (Hobby plan floor, $5 of included usage). A spend cap is set in the Railway dashboard.
- Deploys: `git push` to the connected branch, or `railway up`.

### Backups (required, not optional)

- Nightly job: `sqlite3 /data/planner.db ".backup /data/backups/planner-<date>.db"`, gzip, keep 14 daily copies.
- Railway volume backups enabled as a second layer.
- A weekly download of the newest backup to local/cloud storage, documented in `docs/OPERATIONS.md`.
- Restore procedure written down and exercised once before the first real data is entered.

### Portability

Plain Docker + env config means the same image runs on Fly.io, a VPS, or a home box later. Switching to Vercel + Neon (the $0 option) requires swapping SQLite for Postgres (Drizzle dialect + driver + schema types) and moving the nightly backup to a scheduled job; that is a contained change, deferred by decision.

### Hosts considered and not chosen

Recorded so the choice is not re-litigated: Railway Free ($1/month credit — cannot sustain an always-on app), Vercel+Neon ($0 but cold starts, no free backups, once-daily cron), Cloudflare Workers+D1 (10 ms CPU on free tier breaks SSR; $5 paid), Render free (no persistent disk), Fly.io (~$4.84 but no `git push`), PikaPods (no Asia region, catalog-only), Oracle Always Free / GCP (free but you are the sysadmin), home Pi + Tailscale Funnel ($0 but home uptime + hardware).

## 11. Testing strategy

### Unit (Vitest)

- Palette: 8 distinct shades per family; correct `onContainer` contrast per step; child shade assignment sequence and reuse after delete.
- Permissions: `canWriteCalendar` truth table (owner, partner, ours, view-only, non-member).
- Two-level invariant: rejecting a grandchild, rejecting cross-household parents.
- Time helpers: timed ⇄ UTC conversions, all-day date handling across DST boundaries, range intersection.
- RRULE: validation, `exdates` serialization, scope resolution for "this event".

### Integration (Vitest + in-memory SQLite, migrations applied)

- Route handlers end-to-end: create/rename/delete calendars; create/update/delete events; range queries including recurring rows.
- Household isolation: a member of household B can never read or mutate household A data (tested with a second seeded household).
- View-only: partner PATCH/DELETE on a view-only calendar → 403; owner succeeds; UI-level hiding is not the guarantee.
- Constraints: eighth sub-calendar → 409; grandchild → 400; invalid event shape → 400.

### E2E (Playwright)

- Two browser contexts (both users signed in): create root + sub-calendars, verify shades differ; toggle a person pill and confirm the other's events disappear; view-only calendar shows no edit affordances and direct API call returns 403; drag-create an event in month view; drag it to a new day; create a weekly recurring event and verify it appears next month; skip one occurrence and verify it is gone; mobile viewport smoke test (bottom sheet + agenda).

### Manual

- Phone: iOS Safari and Android Chrome, add to home screen, one full week of real use.
- 2FA enrolment and login with backup code.
- Restore from a nightly backup into a scratch container.

### CI (GitHub Actions)

Lint → typecheck → unit + integration → production build → Playwright (against a built server with a temp DB). Runs on pushes and PRs.

## 13. Decision log

| Decision | Rationale |
|---|---|
| FullCalendar v7 (pinned exact) over Schedule-X / custom grid | Every interaction we need (select-to-create, drag, resize, overlap layout) is free/MIT; RRULE and IANA timezones free; v6 is legacy and v7 is 4 months old with real React SSR. Schedule-X paywalls drag/resize; a custom grid is weeks of fiddly work. |
| Better Auth over Auth.js / managed providers | Sign-up disable + admin provisioning + TOTP plugin are first-class; users stay in our DB; $0. Auth.js is beta, Lucia is discontinued, Clerk gates MFA behind Pro. |
| Drizzle over Prisma | No codegen step, schema is TypeScript, migrations are reviewable SQL; Prisma is mid-rearchitecture in 2026. |
| SQLite over Postgres | One file, no server, trivial backups — correct for two users on one container. Postgres migration is the documented cost of moving to Vercel+Neon. |
| Railway over Vercel+Neon (for now) | Always-on, ~$5–6/month, one dashboard, no cold starts, keeps SQLite. Host decision explicitly deferred; app stays portable. |
| Two levels, not a tree | Solves School→subject and Work→type without a tree UI or recursive visibility rules. |
| Events on both levels | Sub-calendars are optional detail, not a requirement. |
| Auto-assigned shades | Guarantees the visual family reads correctly and re-shades on parent recolour; removes a decision per sub-calendar. |
| Everything visible + view-only flag | The two users are a couple, not adversaries; privacy theatre would add rules without adding safety. The flag protects work calendars from accidental edits. |
| Custom toolbar, FullCalendar header off | The cozy design needs its own top bar with person pills. |
| localStorage for visibility state | Device-local UI preference; avoids a schema and a server round-trip. |

## 14. Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| FullCalendar v7's new CSS/theme system costs more time than budgeted | Medium | Pin exact 7.1.3; start from the bundled `classic` theme and override tokens; timebox theme work and fall back to stock look if it overruns |
| Better Auth + Next 16 peer conflict | Low | Verify at M0; fall back to Next 15.5.x (documented change, no design impact) |
| SQLite volume loss on Railway | Low | Nightly backups + volume snapshots + tested restore (M9) |

## 15. Deferred decisions

Recorded so they are decisions, not omissions:

1. **Final host** — Railway now; revisit after two weeks of real use (Vercel+Neon is the $0 alternative, requiring a Postgres migration).
2. **Postgres migration** — only if we move to Neon or outgrow a single container.
3. **Per-occurrence overrides** (move just this Tuesday's event) — v0.2, needs an exceptions table.
4. **Reminders/notifications** — v0.2; needs a scheduler and an email/push provider.
5. **ICS export/import and Google Calendar sync** — v0.2+, after the data model stops moving.
6. **Dark mode** — later; every token needs a dark counterpart.
7. **PWA / install prompt / offline** — later.
8. **Chinese UI / i18n** — currently English-only; copy is centralised so translation stays cheap.
9. **Attachments, search, tasks/notes modules** — out of scope until the calendar is actually used daily.
10. **More than two users / additional households** — schema allows; product and quota do not.
